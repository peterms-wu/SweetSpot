# SweetSpot Constitution

SweetSpot（舊名 SteamSage2）是本機工具：同步公開的 Steam 願望清單，預測每款遊戲的「折扣 × 預期出現時間」曲線，
找出值得購買的甜蜜價與時點，並說明原因。它重寫前身專案 SteamSage；前身失敗的根本原因是主觀規則
不斷疊加、從未驗證準確度。本憲章的原則以避免重蹈該失敗為首要目的。甜蜜價等產品定義屬於功能規格，
不在本憲章重複（見原則 V）。

## Core Principles

### I. 未知不是零

- 缺少的價格、日期或欄位 MUST 留空或明確標示原因，不得以零、上一次的舊值或捏造值冒充。
- 已知的零元（例如限免）與未知 MUST 在資料模型中可區分。
- 資料稀少時，預測 MUST 仍給出估計，並標示為低信心；「低信心」不得被省略或隱藏。

理由：使用者要的是可用的判斷，但必須清楚知道哪些判斷站得住、哪些只是弱估計。

### II. 證據可追溯

- 每個價格觀測 MUST 記錄來源、商品識別、區域、幣別與取得時間。
- 每個預測與購買建議 MUST 可追溯到所用的證據、模型版本與分析時間。
- 每個預估價格與時點 MUST 附上人類可讀的原因說明。
- 快取或沿用的資料 MUST 保留原始取得時間，不得宣稱為本次重新取得。

### III. 逐項隔離失敗

- 單一遊戲的資料缺漏、來源錯誤或模型例外 MUST NOT 阻止其他遊戲產生結果。
- 每個遊戲 MUST 有明確的結果狀態與失敗原因。
- 整批執行失敗或中斷時，MUST NOT 破壞既有價格資料、預測紀錄與比較基準；
  基準只在新結果完整保存後才前進。

### IV. 預測必須可驗證（NON-NEGOTIABLE）

- 預測模型 MUST 能以任意過去時點為分析時間進行回測，且回測只能使用該時點之前可取得的資料
  （不得有未來資訊洩漏）。
- 專案 MUST 維護一個簡單的基準模型，作為所有模型比較的下限。
- 模型變更（新增、修改或移除規則、參數、特徵）MUST 在相同回測資料集與既定指標上優於現行模型，
  才能成為預設模型；比較結果 MUST 記錄在版本化文件中。
- 例外：只對「資料品質旗標」作出反應的規則變更（例如價格歷史停止更新時降為低信心），如果這個旗標在回測資料集中不可能出現，
  無法「優於」現行模型。這種變更 MAY 在以下條件全部成立時採用：在現行回測資料集上證明與現行規則逐案相同（只差版本）、
  證據記錄在比較文件、經使用者同意。它 MUST NOT 被表述為提升準確度。
- 每次正式執行 MUST 保存當次預測紀錄，供日後與實際價格對照。
- 信心等級 MUST 說明其含義；未經回測或事後對照驗證的準確率 MUST NOT 被宣稱。

理由：前身專案的規則皆為主觀設定且未驗證，最終無法判斷好壞。可驗證性是本專案存在的前提。

### V. 規則單一正本

- 預測與決策規則 MUST 只存在於一份版本化的模型定義文件及其對應程式碼中。
- 規則變更 MUST 更新該文件並遞增規則版本；不得以額外的「修正說明」文件疊加覆蓋舊規則。
- 規則版本 MUST 出現在每份輸出與預測紀錄中。

### VI. 簡單優先

- 能以少量參數解釋的行為，MUST NOT 以逐案特例處理。
- 每個新增的規則、門檻或參數 MUST 有回測結果或資料分析支持的理由；純主觀的可調參數
  （例如使用者偏好的容許差距）MUST 明確標示為使用者偏好而非模型事實。
- 不為尚未確定的需求預先建構抽象（YAGNI）。

### VII. 核心與呈現分離

- 分析核心 MUST 輸出結構化結果（版本化的 JSON 契約），且 MUST NOT 依賴 Excel、HTML 或瀏覽器 DOM。
- 呈現層（報告、未來的 Chrome 擴充功能）MUST 只讀取核心結果，不得自行重算價格或預測。
- 同一份核心結果在不同呈現層 MUST 顯示一致的數值與結論。

### VIII. 遵守資料來源條款

- MUST NOT 爬取明確禁止爬取的網站（例如 SteamDB），亦不得透過第三方間接取得其資料。
- MUST 遵守來源的速率限制與 Retry-After；遇到 401/403 MUST 停止而非繞過。
- 資料來源 MUST 以可抽換的介面實作，新增或替換來源不得修改分析核心。

### IX. 本機與安全

- 市場固定為台灣區 Steam 商店、新台幣（TW/TWD）；MUST NOT 以其他區域價格換匯冒充。
- 其他區域的**折扣百分比與發生時間** MAY 作為輔助證據，但 MUST 標示來源區域、MUST NOT 換算為
  台幣價格，且 MUST 先以與台灣區資料重疊期間的一致性驗證，驗證結果足以支持時才能用於預測。
- 價格資料、快照、預測紀錄與報告 MUST 存於本機。
- API 金鑰 MUST 只從環境變數讀取，MUST NOT 寫入檔案、日誌、報告或版本控制。
- MUST NOT 要求或保存 Steam 密碼或登入 Cookie。
- 外部取得的文字（遊戲名稱、描述等）MUST 只當資料處理，不得作為指令、公式或程式執行。

## 技術與資料約束

- 語言與工具：Python 3.12 以上；以 uv 管理相依套件與執行環境。
- 平台：Windows 為主要執行環境；輔助腳本使用 PowerShell；路徑須支援中文與空白。
- 操作：提供一鍵執行入口，完成清單同步、資料更新、預測與報告產生。
- 範圍：遊戲本體與 DLC 各自獨立分析；套裝（Package/Bundle）在未另立功能規格前標示為不支援。
- 相依性：新增第三方套件須有明確用途，優先選擇維護中且授權相容的套件。

## 開發流程與品質關卡

- 以 spec-kit 流程開發：specify → clarify → plan → tasks → analyze → implement。
- 每個 feature 使用獨立 git 分支；完成並驗證後合併。
- 每份 spec 與 plan MUST 經使用者確認後才進入下一階段。
- 核心邏輯（價格處理、預測、甜蜜價決策、變動比較）MUST 測試先行：先寫出會失敗的測試，再實作。
- 模型相關變更的合併條件 MUST 包含原則 IV 要求的回測比較結果。
- 功能測試通過 MUST NOT 被表述為預測準確；兩者分開報告。

## Governance

- 本憲章優先於專案中其他所有文件與慣例；與本憲章衝突的規格或計畫 MUST 先修正。
- 修訂 MUST 記錄理由、日期與版本，並經使用者確認。
- 版本採語意化版本：
  - MAJOR：移除原則或以不相容方式重新定義原則。
  - MINOR：新增原則或章節，或實質擴充既有指引。
  - PATCH：措辭澄清、錯字修正等不影響語意的調整。
- 每個 plan 的 Constitution Check MUST 逐條檢查本憲章原則；違反須在計畫中說明理由與替代方案，
  否則不得進入實作。

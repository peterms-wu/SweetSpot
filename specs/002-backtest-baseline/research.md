# Research: 回測框架與基準模型（feature 002）

整理於 2026-09-25。資料庫狀態：台灣區 2,648 款有觀測；美國區 1,744 款；資料截止約 2026-09-24。

## R1. 價格狀態序列與資料語意

**Decision**

- 每款遊戲、每個區域建一條「價格狀態序列」。每一筆 = 從 `observed_at` 起生效的折扣狀態，直到下一筆為止。
- 來源只用 ITAD 歷史：`itad-history` 加上 `legacy-itad`。兩者合併後，依 `observed_at` 去重，同一時間以 `itad-history` 為準。
- **不用** `steam-current`（本工具自己存的現價快照）：
  - 它從 2026-09-24 才開始存，對回測沒有幫助。
  - 它是定期取樣，不是價格變動紀錄。混進序列會製造假的「新折扣事件」。
  - 現價判斷由 feature 003 負責。
- `is_tracking_start` 的那一筆只當作「序列開始時的狀態」，**不是**新折扣事件。
- **季節特賣最大折扣**：只有序列開始時間 ≤ 特賣開始、且特賣結束 ≤ 這款遊戲的資料已知時間（R3）時，才計算這場特賣。
  算法是特賣開始當下生效的狀態，加上特賣期間內所有新狀態，取最大值。
  序列在特賣期間才開始的，不計這場，因為無法證明特賣前是什麼狀態（spec Edge Cases）。
- 限免（cut = 100）算成已知的 100% 折扣。`cut_pct` 為 NULL 的狀態不參與計算。

**Rationale**

- 兩個來源在同一時間點的紀錄完全一致：791 款同時有兩個來源，20,113 組同時間紀錄，折扣不同的是 0 組。所以合併是安全的。
- 去重後，序列的語意和 store-api 的保證一致。

**Alternatives considered**

- 把 `steam-current` 當成序列的一部分：會製造假事件，否決。
- 各來源分開建序列、再挑一條：舊專案匯入的 940 款沒有 `itad-history`，會白白損失資料。

## R2. 未來季節特賣時點

**Decision**

- 時點 = 分析時點之後才**開始**的季節特賣，一路列到分析時點 + 60 個月為止。
  進行中的特賣不列入（spec FR-003 的 clarify 決定）。
- 取得方式分兩種：
  - 正式預測（as_of 為現在）：用 `PriceStore.sales(now)` 取得已公告的特賣，再加上已存的預估。
  - 回測：用 `sales(as_of)`，只會拿到已開始的特賣。
  - 兩種情況，缺少的（季節, 年份）都用 `calendar.estimate_sale()` 從 as_of 以前的特賣推估。
- **哪些季節要列**：as_of 前 18 個月內舉辦過的季節。這樣 2019–2022 不會出現不存在的春特，2023 起才會列春特。
- **評分時的對應**：預測時點以（季節, 年份）對應到行事曆中實際的特賣，用**實際**的結束時間判定結果。
  實際上沒有舉辦的，評分單位標為「未舉辦」，不計分，但在報告中列出數量。
- **預測距離**以預測當下推估的結束時間計算，因為這是分析時點當時就能知道的。

**Rationale**

- FR-010：回測時不得使用事後才公告的日期。`sales(as_of)` 的 contract 已經保證這一點。
- 18 個月的窗口涵蓋了季節特賣之間最長的間隔（冬特到隔年冬特），也能在某個季節停辦後自動停止預估。

**Alternatives considered**

- 用實際日期產生時點：會偷看答案，否決。
- 固定每年四季：會在 2019–2022 產生不存在的春特，拉低分數，否決。

## R3. 評分單位與結果判定

**Decision**

- 評分單位 = 遊戲 × 分析時點 × 折扣等級 d × 時點 k。
- 「等級 d 的新折扣事件」= as_of **之後**生效的非追蹤起點狀態，cut ≥ d，**而且前一個狀態的 cut < d**（跨越進入 ≥ d）。
  as_of 當下已經生效的狀態不算。進行中特賣剩下的期間出現的新事件，算進下一個時點。
  - 要求「跨越」是實作時補上的：ITAD 在原價變動時也會記一筆新狀態，折扣可能不變。
    如果只看 cut ≥ d，as_of 當下正在打 50% 的遊戲，之後一筆「原價變動、仍是 50%」的紀錄就會被誤算成新事件。
  - 例：as_of 時已經是 50%，之後變成 60%：d = 55、60 算新事件；d ≤ 50 不算，要等下一次從 < d 進入 ≥ d。
- 對每個（遊戲, as_of, d），先找出第一次事件的時間 t\*。對時點 k（實際結束時間 E_k）的判定：
  - t\* < E_k → **已發生**
  - 否則，若 E_k > 這款遊戲的資料已知時間 → **截斷**（不計分）
  - 否則 → **未發生**
- **資料已知時間**（逐款遊戲、逐區域）= min(資料集截止時間, 這款遊戲最後一次取得歷史的時間)。
  最後一次取得歷史的時間，取該區最新的 `history_fetches.fetched_at`，以及 `legacy-itad` 觀測的最新 `retrieved_at`，兩者取較晚者。
  為此在 `PriceStore` 新增唯讀方法 `history_known_until(app_id, region)`（contracts/store-api-additions.md）。
  這個值只給評分使用，模型拿不到。
- **模型看得到的證據**：分析時點之前的序列，以及**已結束**（end ≤ as_of）的季節特賣最大折扣。
  進行中的特賣資料不完整，不列入歷史。
  - 台灣區目標：模型可以看台灣區與美國區的序列。
  - 美國區目標：模型只能看美國區（clarify 的決定），由框架限制，不靠模型自律。

**Rationale**

- ITAD 只記錄價格變動。最後一次抓取之後，其實不知道有沒有變。若當成「沒打折」，會把未知算成 0，違反憲章 I。
  實測各款的最後取得時間在 2026-09-20 到 2026-09-25 之間，差距不大，但日後資料更新頻率不同時就會有差。
- 由框架依目標區域決定模型能看到什麼，洩漏測試與 FR-025 的限制才能在框架層驗證。

## R4. 指標

**Decision**

- **Brier**：每個評分單位計算 (p − o)²。先算每款遊戲的平均，再平均所有遊戲。分組時，在組內用同樣的方式計算。
- **分組**：
  - 區域
  - 預測距離：台灣區分 0–3、3–6、6–12 個月；美國區分 12–24、24–36、36–60 個月
  - 折扣等級：每 5 個百分點
  - 信心等級
  - 樣本來源：願望清單、相關樣本、廣泛樣本、舊專案匯入
- **校準表**：預測機率每 0.1 一組，列出加權後的預測平均、實際發生比例（加權方式同 Brier：權重 1/該遊戲的單位數），以及原始單位數。
- **命中率**：對每個（遊戲, as_of, d），點預測 = 累積機率第一次 ≥ 0.5 的時點。
  - 命中 = 在該時點結束前已發生。
  - 點預測的結果為截斷的不計。
  - 整條曲線都沒有到 0.5 的，另外計數為「預測不會發生」，並記錄實際有沒有發生。
- **時間誤差**：點預測的時點序號 − 實際第一次發生的時點序號（單位是場）。
  - 只計兩者都在評估窗口內的情況。
  - 實際在窗口內沒發生、也沒截斷的，另外計數。
- **參照分數**（FR-021）：所有遊戲都用 as_of 以前的整體比例，也就是基準模型的低信心路徑套用在所有遊戲上。
- **比較**：成對重抽樣。每款遊戲的差值 = 新模型的平均 Brier − 現行模型的平均 Brier。依遊戲抽樣 2,000 次，
  取 2.5% 與 97.5% 分位數。種子固定為該區資料集識別碼的前 8 位十六進位，確保可以重現。
  - 判定「優於」：台灣區區間上限 < 0，**而且**美國區區間下限 ≤ 0（FR-029）。
    美國區依 R6 的規則省略時，差距視為 0，也就是「沒有變差」。
  - 同一區域中，兩份結果的評分單位數必須逐款遊戲都相同，否則拒絕比較。

**Rationale**

- 每款遊戲同權重是 clarify 的決定。成對重抽樣可以處理同一款遊戲的評分單位彼此相關的問題。
- 參照分數的成本幾乎是零，但可以回答「逐款遊戲的資訊到底有沒有用」。

## R5. 基準模型的規則與參數

**Decision（規則）**

- 對每個折扣等級 d：p(d) = 本身已結束的季節特賣中，最大折扣 ≥ d 的比例。
- 時點 k 的累積機率 = 1 − (1 − p(d))^k，k 是從分析時點起算的第幾場季節特賣。
- 本身的季節特賣少於 N 場時，p(d) 改用整體比例，也就是資料集所有遊戲在 as_of 以前已結束的季節特賣中，
  最大折扣 ≥ d 的比例（每場特賣同權重），並標示「低信心」。
- 單調性自動符合 FR-004：p(d) 是「≥ d 的比例」，隨 d 加深不遞增；1 − (1 − p)^k 隨 k 不遞減，
  也隨 p 不遞減，所以累積機率隨時間不遞減、隨折扣加深不遞增。
- 參數 1：N。參數 2：歷史來源，`TW` 或 `TW+US`（FR-025）。美國區目標一律只用美國區。

**探索性回測**（`explore_baseline.py`，純 Python，只在研究階段使用，非正式結果）

設定：分析時點為每月 1 日；每款遊戲同權重；資料截止 2026-09-24。
行事曆目前只有 2019 夏特以後，所以美國區的分析時點是 2020-01 到 2025-09。

台灣區（2025-02 到 2026-09，共 20 個分析時點；2,590 款；278 萬個評分單位；兩種變體的評分單位相同）：

| TW，N=2 | 0.1047 | 40,763 / 6,643 |
| TW，N=4 | 0.1325 | 24,182 / 23,224 |

**初步觀察**（正式回測後才寫進模型定義文件）

1. **逐款遊戲的歷史在 12 個月內很有用**：台灣區 N=1 比參照分數低 28%。
2. **合併美國區較舊的歷史，反而讓台灣區的預測變差**（0.1027 → 0.1092）。推測原因是遊戲越舊折扣越深：
   2019–2023 的折扣頻率低估了現在的折扣。這支持 FR-025 預設只用台灣區，但仍要以正式回測與比較判定確認。
3. **基準模型在 1–5 年的長期預測很弱**：N 小的時候比參照分數還差（N=1 是 0.2178，參照是 0.1587）。
   理由同上，經驗頻率沒有考慮「遊戲變老、折扣加深」。這是基準模型的已知限制，也是 feature 004 最明確的改進方向。
   feature 003 用到長期預測時，必須標示這個限制。
4. N 在兩區的最佳值不同（台灣區 1、美國區 6）。基準模型只用一個 N：以台灣區（主要市場）的回測選定，
   美國區用同一個 N 如實報告。不為兩區各設一個 N，避免增加參數（憲章 VI）。

**Decision（參數的決定方式）**

在實作階段以正式框架跑網格：N ∈ {1, 2, 3, 4, 6} × 歷史來源 ∈ {TW, TW+US}。
- 依台灣區 Brier 選出最佳設定。
- 用 `compare` 對其他設定做成對比較，結果寫入 `docs/model/comparisons.md`。
- 選定的設定成為基準模型 v1.0.0 的參數，寫入 `model-definition.md`，附上網格結果作為依據（憲章 VI）。
- 研究階段的預期是「TW、N=1」。若正式結果不同，以正式結果為準，並說明差異。

**Alternatives considered**

- 用貝氏收縮（本身比例與整體比例加權平均）取代硬門檻：通常分數更好，但多一個權重參數，而且使用者已經選了
  「資料少時改用整體比例」。留給 feature 004 以回測證明。
- 依季節（春夏秋冬）分開算頻率：台灣區每季只有 1–2 場，樣本太少。留給 feature 004。

## R6. 回測資料集與可重現性

**Decision**

- **遊戲清單**：資料庫中有台灣區 ITAD 歷史、在資料截止時點的台灣區原價 > 0，而且不是套裝的所有遊戲（參考資料集 + 願望清單）。
  美國區使用同一份清單中有美國區歷史的遊戲。
- 某個分析時點要納入某款遊戲，條件是：該區序列在 as_of 以前已經開始，而且至少有一個時點落在評估窗口內。
- **排程**：
  - 台灣區：從資料中第一場已結束的季節特賣之後的第一個月 1 日開始（目前是 2025-02-01），
    到資料截止前最後一個月 1 日為止。
  - 美國區：規則和台灣區相同，從資料中第一場已結束的季節特賣之後的第一個月 1 日開始（美國區資料最早 2012-09，
    所以約 2012-12-01），到資料截止前 12 個月為止。更晚的時點，1–5 年的評分單位全部都會截斷。
    （實作時從「行事曆的第一場」改成「資料中的第一場」：在沒有任何資料的時點預測沒有意義，兩區規則也因此一致。）
- **資料截止時間**的預設值：資料庫中最新的資料已知時間（R3），取到當天 00:00 UTC。取整到天比較容易重現，
  也方便用 `--cutoff` 指定同一天。
- **資料集識別碼逐區域計算**。每個區域的識別碼是以下內容的 SHA-256：
  - 該區的遊戲清單（排序）
  - 資料截止時間
  - 該區的排程
  - 折扣等級
  - 該區的評估窗口
  - 季節特賣行事曆（評分用的實際特賣起訖）
  - 每款遊戲在該區的資料已知時間
  - 該區目標**可以看到的**所有觀測的（app, region, observed_at, cut_pct, is_tracking_start）。
    台灣區目標可以看到台灣區與美國區（R3），所以台灣區的識別碼包含兩區的觀測；美國區只包含美國區。

  任何一項改變，該區的識別碼就改變。
- **逐區域比較**（FR-028）：
  - `compare` 逐區比較兩份結果都有的區域，識別碼不同就拒絕。台灣區必須兩份都有。
  - 只有一份有美國區時，只有在兩個模型的名稱與版本相同、參數差異全部屬於模型宣告的 `tw_only_params`
    （基準模型是 `{"history"}`）時才可以比較。此時美國區的差距視為 0，紀錄中註明「美國區結果依構造相同，未重跑」。
    其他情況一律拒絕。
  - 這讓 R5 的網格可以只對「台灣區 + 美國區」變體跑台灣區，不必重跑相同的美國區回測。
- **重現性**：
  - 所有迭代都依排序後的遊戲 ID 與時間進行。
  - 重抽樣用固定種子。
  - 輸出 JSON 以排序後的鍵寫入。

  同一模型版本、同一資料集重跑，結果檔內容相同（執行時間與耗時欄位除外）。
- **原子寫入**：先寫 `*.json.tmp`，完成後改名。中斷時只留下 `.tmp`，不會被當作結果讀取。

**Rationale**

- 資料庫每天都在長大。只記錄截止時間不夠，因為之後補抓的參考遊戲可能帶來截止時間以前的觀測。所以要對實際使用的觀測做雜湊。
- 排程從第一場已結束的特賣之後開始：探索時發現，2025-01-01 那個時點台灣區沒有任何歷史。
  只有合併美國區的變體能給出預測，兩種變體的評分單位因此不同，無法成對比較。

## R7. 效能與實作方式

**Decision**

- 一次讀進每款遊戲到資料截止為止的序列：兩個 SQL 查詢，約 22 萬列，1.2 秒。之後在記憶體中依 as_of 截斷，再交給模型。
- 不再對每個分析時點重查資料庫：探索時的做法若改成每個時點查一次，要 1,750 款 × 150 個時點 = 26 萬次查詢。
- 「在記憶體中截斷」是效能最佳化，不改變語意。由洩漏測試保證截斷結果與 `PriceStore.observations(as_of)` 完全一致：
  在人工資料庫上，兩種方式產生的預測必須逐位元相同。
- 整體比例在每個分析時點只算一次（PopulationView 快取），不在每款遊戲重算。
- 純 Python，不引入 numpy。探索時兩區、12 個設定共約 50 秒。

## R8. 行事曆補齊 2012–2018 季節特賣（FR-033）

**Decision**：把 [research-calendar-2012-2018.toml](research-calendar-2012-2018.toml) 的 21 場季節特賣
依日期加入 `data/steam_sales.toml`，放在 2019 農曆新年特賣之前。只貼 `[[sale]]` 條目，不貼檔尾的研究註記。

| 年 | 夏特 | 秋特 | 冬特 |
|---|---|---|---|
| 2012 | 07-12 → 07-23 | 11-21 → 11-27 | 12-20 → 2013-01-05 |
| 2013 | 07-11 → 07-22 | 11-27 → 12-03 | 12-19 → 2014-01-02 |
| 2014 | 06-19 → 06-30 | 11-26 → 12-02（Exploration Sale） | 12-18 → 2015-01-02 |
| 2015 | 06-11 → 06-22 | 11-25 → 12-01（Exploration Sale） | 12-22 → 2016-01-04 |
| 2016 | 06-23 → 07-04 | 11-23 → 11-29 | 12-22 → 2017-01-02 |
| 2017 | 06-22 → 07-05 | 11-22 → 11-28 | 12-21 → 2018-01-04 |
| 2018 | 06-21 → 07-05 | 11-21 → 11-27 | 12-20 → 2019-01-03 |

（end 是恢復原價的時間，太平洋時間 10:00）

- **來源**：21 場都是 `official`。起訖日期都有 Valve 自己的公告佐證，大多來自仍可開啟的舊版 Steam News
  （`store.steampowered.com/oldnews/<id>`）。沒有使用 SteamDB。
- **驗證**：
  - 合併後的暫存副本以正式的 `load_calendar()` 載入成功：共 151 場，季節特賣 51 場，沒有驗證錯誤。
  - 抽查 oldnews/8388 與 oldnews/26499，都是 HTTP 200，內容與條目一致。
- **判斷與取捨**（詳見檔尾註記）：
  - 2014、2015 的 Exploration Sale 是感恩節檔期的全站特賣，歸為秋特；名稱保留 Valve 原名。
  - 2012–2014 的 Holiday Sale 就是冬特的舊名。
  - 2012–2018 沒有春特：Spring Indie Sale、VR Spring Sale、Spring Cleaning 都不是全站特賣。
    這與 001 研究的「2019–2022 沒有春特」一致。
  - 2012、2013 冬特結束後另有 1–2 天、只有幾十款遊戲的 Encore，不併入 `end`。
  - 2016、2017 冬特公告寫「10pm」，有多項 Valve 自己的佐證指出是筆誤，採 10:00。
- **對模型的影響**：2015 夏特以前的季節特賣有每日特價與限時搶購，同一款遊戲在特賣期間可能多次變價。
  「特賣期間的最大折扣」這個定義（R1）本來就涵蓋這種情況，不需要特別處理，但美國區早期的特賣
  最大折扣可能比後期高，這一點在回測報告的美國區限制中註明。

**Alternatives considered**：從價格資料反推特賣日期。否決，理由見 spec clarify：違反「行事曆每場附來源」的原則。

## R9. 模型定義、比較紀錄與現行模型

**Decision**

- `docs/model/model-definition.md` 是唯一的規則正本（憲章 V），每個模型一節，內容包括：
  - 名稱、版本、參數與依據（回測數據）
  - 規則
  - 信心等級的判定條件與回測分數
  - 已知限制
  - 版本歷史
- `docs/model/comparisons.md` 只附加。每筆紀錄包括：
  - 日期、資料集識別碼
  - 兩個模型的名稱、版本、參數
  - 兩區的 Brier 與差距、區間、判定與理由
  - 回測結果檔名
- 現行模型寫在程式的 `CURRENT_MODEL` 常數中（名稱、版本、參數），**不放在使用者設定檔**，避免未經比較就換模型。
  有一個測試會檢查：`comparisons.md` 中必須有一筆紀錄，判定現行模型被採用；基準模型是第一筆，紀錄為「建立下限」。
- 版本規則：規則或參數改變時遞增版本（語意化版本），預測輸出的欄位改變時遞增契約版本。
- **評分框架設定**另立一節，並標明它們是**框架設定、不是模型參數**：
  - 18 個月的季節窗口、60 個月的輸出範圍（R2）
  - 評估窗口（台灣區 0–12 個月、美國區 12–60 個月）
  - 0.5 的點預測門檻、0.1 的校準分組、2,000 次重抽樣（R4）

  這些設定只附推理依據，不調整來讓模型分數變好。修改任何一項都會改變資料集識別碼（窗口與排程）或比較方法，
  必須在這一節記錄理由與日期。
- **第一個現行模型**（FR-031 的例外）：以「建立下限」紀錄設定，參數取網格中台灣區 Brier 最低的設定，
  不要求顯著優於其他設定；網格結果全部寫進比較文件。

## R10. 指令與輸出

**Decision**

- 新增 3 個唯讀指令，不取寫入鎖，以唯讀方式開啟資料庫（contracts/cli.md）：
  - `steamsage forecast [--as-of 日期] [--app ID]… [--out 檔案]`：預設對願望清單、以現在為分析時點，輸出 `steamsage.forecast/1` JSON。
  - `steamsage backtest [--model 名稱] [--param k=v]… [--region TW|US|all] [--cutoff 日期]`：結果寫入 `data/backtests/`。
  - `steamsage compare 結果A 結果B [--record]`：`--record` 時附加寫入 `comparisons.md`。
- 目前 `cli.main()` 對每個指令都會開啟 `StoreWriter`，唯讀指令要改成不開啟寫入器。
- `forecast` 的輸出不是正式預測紀錄。保存預測紀錄屬於 feature 003。

# Feature Specification: Chrome 擴充功能

**Feature Branch**: `011-chrome-extension`

**Created**: 2026-09-27

**Status**: Draft

**Input**: User description: "Chrome 擴充功能（feature 011），秋特（2026-10-02 01:00 台北開始）前可用。每次 report 另外寫一份精簡資料檔到擴充功能資料夾，
擴充功能讀自己的檔案；工具列彈出視窗（點圖示才打開，圖示顯示「現在買」數量）、遊戲頁面購買區上方的面板、願望清單每列名稱下方一行；
只顯示核心算好的內容並列頁面即時價格，不判斷「已到價」；每日排程改到 02:30；只給使用者本人用、只支援 Chrome、不連外部網站。"

## 範圍說明

專案目標的 roadmap 第一項是「在 Steam 願望清單頁上直接看到甜蜜價」。目前要看建議只能開 HTML 報告；使用者在秋特期間是在 Steam 網站上逛，
需要在逛的同時看到每款遊戲的分組、甜蜜價與甜蜜時點。憲章 VII 從一開始就要求核心輸出版本化的結構化結果、呈現層只讀它，這個 feature 就是第二個呈現層。

2026-09-27 的可行性檢查（唯讀）：

| 檢查 | 結果 |
|---|---|
| 願望清單頁 | 由 Steam 的前端程式產生，樣式名稱沒有意義、會隨改版變動；每一列有指向遊戲頁的連結（含 App 編號），可以用它對應遊戲；列表只畫出看得到的約 9 列，捲動時才產生新的列 |
| 遊戲頁 | 購買區的結構多年沒變；每個購買選項帶有它的套件或組合包編號，可以對應到核心追蹤的那一個；未登入時部分遊戲先出現年齡確認頁 |
| 資料量 | 每天的正式紀錄約 1 MB；擴充功能需要的欄位約 180 KB |
| 時間 | 2026 秋特：台北 10/2 01:00 – 10/9 01:00；目前每日排程在 00:00，開賣第一天的資料會是開賣前的狀態 |

- **包含**：
  - 核心每次正式產生報告時，另外寫一份給擴充功能用的資料檔（版本化的格式，只含顯示需要的欄位）。
  - 擴充功能的三個呈現位置：工具列彈出視窗（含圖示上的數量）、遊戲頁面的面板、願望清單頁每列的一行。
  - 資料時間的顯示與「資料過舊」的提示。
  - 每日排程由 00:00 改到 02:30。
  - 安裝與使用說明（README、HANDOFF）。
- **不包含**：
  - 到價提醒（通知）、在擴充功能中觸發資料更新、組合包頁面、其他瀏覽器、上架到線上應用程式商店。
  - 擴充功能自行判斷「已到價」或重算任何價格與機率（憲章 VII）。
  - 模型、決策規則、組合包規則與報告內容的任何改變。
- **不變**：
  - 預測與決策（`steamsage.decision/2`）、正式紀錄、HTML 報告的內容與數字。
  - 每日更新的內容（只改排程時間）。

## Clarifications

### Session 2026-09-27（specify 前，與使用者確認）

- Q: 資料怎麼傳到擴充功能？ → A: 每次報告另外寫一份精簡資料檔到擴充功能自己的資料夾，擴充功能讀自己的檔案；不用本機伺服器，也不用瀏覽器與本機程式的溝通管道。
  plan 必須驗證報告改寫資料檔之後，Chrome 不必重新載入擴充功能就會讀到新資料。
- Q: 顯示在哪裡？ → A: 三個位置都做：工具列彈出視窗（只在點圖示時打開，圖示上顯示「現在買」的數量）、遊戲頁面購買區正上方的面板、
  願望清單每一列遊戲名稱下方的一行（分組顏色、滑鼠移上顯示原因）。
- Q: 顯示什麼？ → A: 只顯示核心算好的內容，並列頁面上的即時價格；擴充功能不判斷「已到價」（憲章 VII）。
- Q: 秋特期間的資料新鮮度？ → A: 每日排程改到 02:30（Steam 特賣在台北 01:00 或 02:00 開始或換日）。
- Q: 範圍？ → A: 只給使用者本人用（開發人員模式載入、不上架）、只支援 Chrome、擴充功能不連任何外部網站、不讀也不送出 Steam 登入資料。

### Session 2026-09-27（clarify）

- Q: 「資料超過 26 小時」要從哪個時間算起？ → A: 從價格抓取時間算：取所有遊戲現價最後確認時間（`current.confirmed_at`，報告上的「最後確認」）的中位數，門檻 26 小時；
  報告產生時間另外顯示。資料檔也帶每日更新失敗的說明（`data_refresh`），三個位置都顯示。原因：`update` 失敗時 `report` 照跑，報告時間是新的、價格卻是舊的。
- Q: 工具列圖示上的「現在買」數字什麼時候更新？ → A: Chrome 啟動、打開彈出視窗、載入 Steam 遊戲頁或願望清單頁時，以及每 30 分鐘，都重新讀資料檔（只讀本機檔案、不連網）。
- Q: 秋特期間買了遊戲、資料還沒更新前，已擁有的遊戲怎麼顯示？ → A: 遊戲頁出現 Steam 的「已在收藏庫中」標示時，面板縮成一行「你已擁有這款遊戲；以下是購買前（資料時間）的建議」，
  可以展開；只看頁面上的標示，不讀登入資料。圖示與彈出視窗等下次更新，彈出視窗提示買完可執行 `更新資料.cmd` 立即更新。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在遊戲頁面看到這款遊戲的甜蜜價 (Priority: P1)

使用者在秋特期間點進「光與影：33號遠征隊」的 Steam 頁面。購買區正上方出現一塊 SteamSage2 面板：「現在買」、頁面上的現價 NT$790 與甜蜜價 NT$790（−20%）並列、
甜蜜時點 2026 秋特與到價機率、12 個月內最低價、組合包建議（可和 Dispatch 一起買，2026 秋特約 NT$1,063）、其他版本的數量，可以展開看原因；
面板註明資料時間。使用者不用離開 Steam 就能決定要不要買。

**Why this priority**: 秋特期間最常看的頁面，決定「買不買」的那一刻就在這裡。

**Independent Test**: 用真實資料，在 10 款願望清單遊戲的頁面上，面板的數字和報告完全相同；頁面現價是同一個購買選項在頁面上的價格；不在資料中的遊戲頁面沒有任何變化。

**Acceptance Scenarios**:

1. **Given** 一款在資料中、分組為「即將到價」的遊戲，**When** 打開它的頁面，**Then** 購買區上方出現面板，顯示分組、頁面現價與甜蜜價、甜蜜時點與機率、12 個月內最低價與資料時間，數字和報告相同。
2. **Given** 這款遊戲在一個同時含多款願望清單遊戲的組合包中，**When** 打開頁面，**Then** 面板顯示組合包的建議句（和報告相同）。
3. **Given** 使用者指定了其他版本的遊戲（例如 Cyberpunk 2077 終極版），**When** 打開頁面，**Then** 面板註明追蹤的是指定的版本，頁面現價取那個版本的購買選項；頁面上找不到那個選項時不顯示頁面現價，並說明原因。
4. **Given** 一款分組為「無法預測」的遊戲，**When** 打開頁面，**Then** 面板只顯示原因（例如尚未發行）。
5. **Given** 一款不在資料中的遊戲，**When** 打開頁面，**Then** 頁面完全沒有變化。
6. **Given** 年齡確認頁，**When** 使用者通過確認進入遊戲頁，**Then** 面板照常出現；年齡確認頁本身不顯示面板。
7. **Given** 使用者剛買了這款遊戲、資料還沒更新（頁面顯示「已在收藏庫中」），**When** 打開頁面，**Then** 面板縮成一行註明已擁有與資料時間，可以展開。

### User Story 2 - 點工具列圖示看整份清單 (Priority: P1)

使用者在任何網頁點 Chrome 工具列上的 SteamSage2 圖示，彈出一個小視窗：依「現在買／即將到價／繼續等／低信心／無法預測」分組列出遊戲（名稱、現價、甜蜜價、甜蜜時點、機率），
下面是組合包一節，最上面是資料時間。點遊戲名稱會開啟它的 Steam 頁面。沒有點圖示時，擴充功能不會跳出任何東西；圖示上的小數字是「現在買」的款數。

**Why this priority**: 不依賴 Steam 頁面結構，Steam 改版也不會壞，是最可靠的入口；圖示上的數字讓使用者一眼知道有沒有該買的。

**Independent Test**: 用真實資料打開彈出視窗，每組款數與報告相同，圖示數字等於「現在買」的款數；資料檔不存在時顯示如何產生資料的說明。

**Acceptance Scenarios**:

1. **Given** 最新資料，**When** 點圖示，**Then** 彈出視窗依分組列出所有願望清單遊戲，每組款數與報告相同，另有組合包一節與資料時間。
2. **Given** 最新資料中「現在買」有 11 款，**When** 使用者看工具列，**Then** 圖示上顯示「11」；「現在買」為 0 款時不顯示數字。
3. **Given** 使用者沒有點圖示，**When** 瀏覽任何網頁，**Then** 擴充功能不彈出任何視窗或通知。
4. **Given** 資料檔不存在或格式不認得，**When** 點圖示，**Then** 彈出視窗說明「還沒有資料，請先執行更新」或格式不符的原因，不顯示舊的或捏造的內容。

---

### User Story 3 - 在願望清單頁每一列看到分組與甜蜜價 (Priority: P2)

使用者打開自己的 Steam 願望清單，每一列遊戲名稱下方多一行：分組（顏色區分）、甜蜜價、甜蜜時點、到價機率；在組合包中的遊戲多一個「組合包」標記；
滑鼠移到這一行上會顯示前幾個原因。捲動到下面新出現的列也有這一行。

**Why this priority**: 一眼掃過整份清單很方便，但頁面結構由 Steam 決定、最容易因改版失效，所以排在遊戲頁面與彈出視窗之後。

**Independent Test**: 從頭捲到尾，每一列在資料中的遊戲都恰好有一行，不在資料中的沒有；頁面結構改變（用改過的頁面副本測試）時不顯示、不出錯，Steam 原本的內容不受影響。

**Acceptance Scenarios**:

1. **Given** 願望清單頁，**When** 頁面載入，**Then** 看得到的每一列在資料中的遊戲，名稱下方出現一行，內容和報告相同。
2. **Given** 使用者往下捲動，**When** 新的列出現，**Then** 新的列也在一秒內出現這一行；同一列不會出現兩行。
3. **Given** 滑鼠移到這一行，**When** 停留，**Then** 顯示這款遊戲的前三個原因。
4. **Given** Steam 改版、找不到遊戲名稱的位置，**When** 頁面載入，**Then** 不顯示任何一行，頁面照常可用，也沒有錯誤影響 Steam 的功能。

### User Story 4 - 知道資料是什麼時候的 (Priority: P2)

秋特第一天，每日排程在 02:30 更新（特賣 01:00 已開始），使用者早上看到的資料時間是當天 02:30。如果電腦前一晚關機、排程沒跑，
彈出視窗、面板與清單上的資料會標示「資料超過 26 小時」，提醒使用者先執行更新。

**Why this priority**: 秋特期間價格在開賣時改變；看到舊資料而不自知，會做出錯的決定。

**Independent Test**: 資料時間在 26 小時以內時沒有提示；超過時三個位置都有提示；排程的下一次執行時間是 02:30。

**Acceptance Scenarios**:

1. **Given** 每日排程，**When** 查看排程，**Then** 每天 02:30 執行，其餘設定（背景、不開報告、錯過時補跑）不變。
2. **Given** 資料時間是 27 小時前，**When** 打開彈出視窗或遊戲頁，**Then** 顯示「資料超過 26 小時，請先執行更新」，內容照常顯示。
3. **Given** 報告剛重新產生，**When** 使用者重新打開彈出視窗或重新載入頁面，**Then** 看到新的資料時間，不必重新載入擴充功能或重開瀏覽器。

### Edge Cases

- **資料檔不存在、損壞或版本不認得**：三個位置都不顯示遊戲資料；彈出視窗說明原因與如何產生資料（憲章 I：不顯示捏造或舊的內容）。
- **資料正在被改寫時讀取**：讀到不完整的檔案時當成「暫時讀不到」，下次打開再讀；核心寫檔要先寫暫存檔再改名，確保不會讀到一半的檔案。
- **非正式執行**（`--as-of`、`--rule` 預覽）：不改寫擴充功能的資料檔，避免預覽蓋掉正式結果。
- **頁面上有多個購買選項**（標準版、豪華版、組合包）：頁面現價取核心追蹤的那一個（依套件或組合包編號對應）；找不到時不顯示頁面現價並說明。
- **已經買了、資料還沒更新**：遊戲頁面板縮成一行註明已擁有（FR-013a）；圖示數字與彈出視窗要到下次更新才改變（已擁有的遊戲會從 Steam 願望清單移除）。
- **遊戲正在打折**：頁面現價就是折扣後的價格；面板只並列，不判斷是否到價。
- **免費、尚未發行或無法預測的遊戲**：面板與清單只顯示分組「無法預測」與原因。
- **其他人的願望清單頁**：只在資料中的遊戲顯示一行；使用者自己的願望清單以外也一樣運作，沒有額外行為。
- **Steam 的語言或幣別不是台灣區**：擴充功能照樣顯示核心的台幣資料；頁面現價只在頁面顯示新台幣時並列，其他幣別不並列（憲章 IX：不換匯）。
- **願望清單很長**：捲動時持續處理新出現的列，不因清單長度變慢。
- **擴充功能出錯**：只影響它自己的顯示，不阻止 Steam 頁面運作（憲章 III 的精神）。

## Requirements *(mandatory)*

### Functional Requirements

**資料檔**

- **FR-001**: 每次正式產生報告（會保存正式紀錄的那一次）時，系統 MUST 另外寫一份擴充功能用的資料檔到擴充功能資料夾：
  有自己的格式名稱與版本，內容只來自同一次的決策輸出（分組、現價、甜蜜價、甜蜜時點與機率、12 個月內最低價、原因、標籤、追蹤的版本、其他版本數量、
  非季節預測的說明、所屬組合包、組合包一節、資料時間與分析時間）。檔案先寫到暫存檔再改名。
- **FR-002**: 非正式執行（指定分析時點、規則預覽）MUST NOT 改寫這個資料檔。
- **FR-003**: 資料檔 MUST NOT 含任何金鑰或登入資訊；它含願望清單內容，所以 MUST 被版本控制排除。

**擴充功能的共通要求**

- **FR-004**: 擴充功能 MUST 只讀自己資料夾中的資料檔；MUST NOT 連任何外部網站、MUST NOT 讀取或送出 Steam 的 Cookie 與登入資料；只在 Steam 商店網站的願望清單頁與遊戲頁執行頁面內容（憲章 IX）。
- **FR-005**: 擴充功能 MUST NOT 重算價格或機率，也 MUST NOT 判斷是否已到價；數字與句子都來自資料檔，擴充功能只做格式化（千分位、百分比、台北時間）（憲章 VII）。
- **FR-006**: 報告改寫資料檔之後，下一次打開彈出視窗或載入頁面 MUST 讀到新資料，不需要重新載入擴充功能或重開瀏覽器（plan 以原型驗證做法）。
- **FR-007**: 「資料時間」是價格抓取時間：所有遊戲現價抓取時間的中位數（由核心寫進資料檔，擴充功能只比較現在時間）。資料時間超過 26 小時時，三個位置 MUST 顯示
  「資料超過 26 小時，請先執行更新」，內容照常顯示；報告產生時間另外顯示。這次正式報告前的每日更新失敗時（資料檔帶核心的說明句），三個位置 MUST 顯示該說明。
  資料檔不存在、損壞或版本不認得時 MUST 說明原因，不顯示任何遊戲資料。
  （2026-10-22 稽核補記：願望清單的行實際只在行首加「資料過舊 ·」，不是完整那句；彈出視窗與遊戲頁面板是完整那句。見 contracts/extension-ui.md「願望清單的行」，011 T031／T032）
- **FR-008**: 擴充功能的錯誤 MUST 只影響它自己的顯示，不改變、不阻擋 Steam 頁面的原有內容與操作。

**工具列彈出視窗**

- **FR-009**: 只在使用者點擴充功能圖示時打開；MUST NOT 自動彈出任何視窗或通知。
- **FR-010**: 內容：資料時間；依五個分組列出遊戲（名稱、現價、甜蜜價與折扣、甜蜜時點、到價機率；「無法預測」顯示原因），每組款數和報告相同；組合包一節（名稱、建議句或多付金額）。
  點遊戲或組合包名稱開啟它的 Steam 頁面。彈出視窗註明「買完遊戲後可執行 `更新資料.cmd` 立即更新」（已擁有的遊戲要到下次更新才離開清單）。
- **FR-011**: 圖示上 MUST 顯示「現在買」的款數；0 款時不顯示；資料過舊或讀不到時以不同的樣式提示。擴充功能 MUST 在 Chrome 啟動、打開彈出視窗、
  載入 Steam 遊戲頁或願望清單頁時，以及每 30 分鐘重新讀資料檔並更新圖示（只讀本機檔案）；報告改寫資料檔後，圖示最遲 30 分鐘內反映新資料。

**遊戲頁面面板**

- **FR-012**: 只在資料中的遊戲頁面（`/app/<App 編號>/`）顯示，位置在購買區正上方；年齡確認頁不顯示；不在資料中的遊戲頁面 MUST 完全不變。
- **FR-013**: 內容：分組；頁面現價與甜蜜價並列（頁面現價取核心追蹤的購買選項在頁面上的價格，依套件或組合包編號對應，找不到或不是新台幣時不顯示並說明）；
  甜蜜時點與到價機率；12 個月內最低價；追蹤的版本（使用者指定時註明）；其他版本的數量；組合包建議；非季節預測的一句話；可展開的全部原因；資料時間。
  「無法預測」只顯示原因。
- **FR-013a**: 遊戲頁出現 Steam 的「已在收藏庫中」標示時，面板 MUST 縮成一行「你已擁有這款遊戲；以下是購買前（資料時間）的建議」，可以展開看完整內容；
  判斷只看頁面上的標示，不讀登入資料（FR-004）。

**願望清單頁**

- **FR-014**: 每一列在資料中的遊戲，在遊戲名稱下方加一行：分組（顏色區分）、甜蜜價與折扣、甜蜜時點、到價機率；在組合包中的遊戲加「組合包」標記；滑鼠移上顯示前三個原因。「無法預測」的遊戲只顯示分組與第一個原因（和 FR-013 一致）。
- **FR-015**: 列表捲動時新出現的列 MUST 在一秒內加上這一行；同一列 MUST NOT 出現兩行；已經處理過的列被 Steam 重新產生時照樣處理。
- **FR-016**: 找不到遊戲名稱的位置時 MUST 不顯示這一行（不猜位置），也不影響其他列與頁面。

**排程與文件**

- **FR-017**: 使用者電腦上的每日背景更新排程 MUST 改到每天 02:30；背景執行、不開報告、錯過時補跑等設定不變。
- **FR-018**: README MUST 說明如何安裝（開發人員模式載入資料夾）、三個位置的內容、資料何時更新與過舊提示、隱私（不連外、不讀登入資料）；HANDOFF 同步更新。

### Key Entities

- **擴充功能資料檔**：一次正式報告的精簡版；有格式名稱與版本、分析時間（報告產生時間）、資料時間（現價抓取時間的中位數）、每日更新失敗的說明、每款遊戲的顯示欄位、組合包一節。
- **遊戲顯示資料**：App 編號、名稱、分組、現價、甜蜜價與折扣、甜蜜時點與機率、12 個月內最低價、原因、標籤、追蹤的版本（套件或組合包編號、是否使用者指定）、其他版本數量、所屬組合包、非季節預測的一句話。
- **組合包顯示資料**：編號、名稱、分級、組合包折扣、現價、建議句或多付金額、內容名稱。
- **頁面現價**：遊戲頁面上，核心追蹤的購買選項當下顯示的價格；只用於並列，不參與任何判斷。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用真實資料，彈出視窗列出的遊戲與每組款數和當天的報告 100% 相同；圖示數字等於「現在買」的款數。
- **SC-002**: 抽查 10 款願望清單遊戲的頁面，面板的分組、甜蜜價、甜蜜時點、機率、12 個月內最低價與組合包建議和報告 100% 相同；頁面現價和頁面上同一個購買選項的價格相同。
- **SC-003**: 願望清單頁從頭捲到尾，資料中的每一列恰好一行（0 重複、0 遺漏），不在資料中的列 0 行；在結構被改過的頁面副本上 0 行、Steam 原有內容不變、沒有錯誤影響頁面。
- **SC-004**: 報告重新產生後，不重新載入擴充功能，下一次打開彈出視窗或重新載入頁面就顯示新的資料時間；圖示數字最遲 30 分鐘內更新（實測記錄）。
- **SC-005**: 擴充功能執行期間對外網路請求 0 次（端對端測試記錄所有請求）；資料檔中不含金鑰。
- **SC-006**: 彈出視窗在 1 秒內顯示；遊戲頁面面板與願望清單的行在頁面內容出現後 1 秒內出現。
- **SC-007**: 報告產生時間因寫資料檔增加 ≤ 0.5 秒；資料檔 ≤ 500 KB。
- **SC-008**: 2026-10-02 01:00 秋特開始前，擴充功能已安裝在使用者的 Chrome 上並經使用者確認可用；排程的下一次執行時間是 02:30。
- **SC-009**: 決策輸出、正式紀錄與 HTML 報告在本 feature 前後，同一份資料上 100% 相同（擴充功能資料檔是新增的檔案）。

## Assumptions

- 使用者使用 Windows 上的 Chrome（目前 154 版），以開發人員模式載入本機資料夾；Chrome 可能在啟動時提醒開發人員模式的擴充功能，這是預期的。
- Steam 商店以台灣區、新台幣顯示給使用者（登入的台灣帳號）；頁面結構以 2026-09-27 為準，之後改版可能讓願望清單的行消失（FR-016 保證不出錯）。
- 「資料過舊」門檻 26 小時 = 每日排程間隔 24 小時加 2 小時緩衝，從價格抓取時間（中位數）算，不從報告產生時間算；
  和 `sweet-price` 的單款現價過舊（24 小時，核心判斷、已在決策輸出中）是不同用途。
- 分組名稱與顏色是呈現層的格式（和 HTML 報告一致），不是核心的判斷。
- 擴充功能的程式碼放在專案中並納入版本控制；資料檔不納入。
- 核心與報告的程式、模型、規則都不變；擴充功能是憲章 VII 所說的「未來的 Chrome 擴充功能」呈現層。

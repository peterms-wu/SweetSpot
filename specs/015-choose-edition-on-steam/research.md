# Research: 在 Steam 遊戲頁直接指定追蹤版本

**Feature**: 015-choose-edition-on-steam | **Date**: 2026-10-14 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

## R0 原型（這台電腦、Playwright 的 Chromium）

`prototype/p1_native.py`：在暫存資料夾產生原型擴充功能（`prototype/ext/`，加上 manifest `key`）、`.bat` 本機程式（`prototype/host_probe.py`，
只用標準函式庫）與本機程式的登記檔；在 HKCU 登記測試名稱 `com.sweetspot.prototype`，跑完刪除（也在失敗時刪除）。Steam 頁面用靜態測試頁。

```
uv run --with playwright==1.63.0 python specs/015-choose-edition-on-steam/prototype/p1_native.py
```

2026-10-14 結果：**16/16** 通過。第一次執行留下兩個空的上層鍵（`Software\Chromium\NativeMessagingHosts`、
`Software\Google\Chrome for Testing\NativeMessagingHosts`，Playwright 的瀏覽器原本沒有），已刪除；原型改成也刪除自己建立的空上層鍵，
重跑（`--skip-long`）14/14，登錄回到原狀。端對端測試照同樣的規則清理（R9）。

| 問題 | 結果 |
|---|---|
| K manifest `key` 能不能固定擴充功能編號 | 可以：編號 = 公鑰 DER 的 SHA-256 前 32 個十六進位字元換成 a–p，載入前就能算出來，和 Chromium 給的一致 |
| V Chromium 讀哪個登錄位置 | `Software\Chromium\…` 與 `Software\Google\Chrome\…` 都讀得到；`Google\Chrome for Testing` 讀不到。使用者的 Chrome 讀 `Software\Google\Chrome\…`（Chrome 文件） |
| H `.bat` 本機程式 | 可以。Chrome 傳入的參數是 `chrome-extension://<編號>/` 與 `--parent-window=0`；工作目錄是 `.bat` 所在的資料夾；用專案 `.venv` 的 python 時，每次 `sendNativeMessage`（每次都是新程序）來回 89–99 ms |
| H 沒有登記時的錯誤 | `Specified native messaging host not found.`（擴充功能據此判斷「沒有安裝」） |
| C 內容腳本 → Service Worker → 本機程式 | 可以，96 ms；Service Worker 看得到送出請求的分頁網址（`sender.url`） |
| T 頁面程式的模擬點擊 | 6 種方式（`click()`、`dispatchEvent` 滑鼠／指標事件、`HTMLElement.prototype.click.call`、模擬 Enter 按鍵、`<label>` 轉送）都不是 `isTrusted`，或根本不觸發；真正的滑鼠、Enter、空白鍵都是 `isTrusted`。不信任的點擊在原型中不會送出請求 |
| L 程序什麼時候結束 | Service Worker 被停止、連線被中斷、`sendNativeMessage` 時 Worker 被停止：本機程式**都沒有被結束**，工作照樣做完、回覆、讀到 EOF 後自己結束。另開的子程序也照樣做完 |
| L 40 秒的工作 | `connectNative` 與 `sendNativeMessage` 都在 40.15 秒收到回覆（Worker 的 30 秒閒置限制不會中斷等待中的本機程式呼叫） |

其他實測：

- 本機程式載入 steamsage（`import steamsage.commands, steamsage.cli`）：361–427 ms。
- 2026-10-14 背景更新的 `report`：5.9 秒。所以一次指定預計約 7 秒（啟動 0.1 秒＋載入 0.4 秒＋報告 6 秒＋驗證與寫檔），spec SC-001 上限 30 秒。

沒有測到的：**Chrome 本身在處理途中關閉**（或電腦關機）時本機程式會不會被結束。見 R5 的處理。

## R1 擴充功能編號（決定 D1：使用者確認 A，2026-10-14）

本機程式的登記檔只允許列出的擴充功能編號（不能用萬用字元），所以本機程式要知道編號。

- **建議 A：manifest 加 `key`**。編號固定，和資料夾位置無關（R0 K）。加上去之後編號會**改變一次**：使用者要在 `chrome://extensions` 重新載入一次
  （擴充功能沒有存任何狀態，只有計時器，重新載入後自己重建）。`key` 是公鑰，可以進版控與 014 公開；私鑰只在產生時用一次，不保存
  （未封裝的擴充功能不需要私鑰）。風險：知道公鑰的人可以做出同編號的擴充功能，但必須能在這台電腦的 Chrome 載入未封裝擴充功能，這時對方已經能直接改設定檔，
  不是新的風險。
- B：安裝指令帶 `--extension-id`，使用者從 `chrome://extensions` 複製。manifest 不變，但多一個手動步驟，擴充功能資料夾搬家後要重新安裝。
- C：由資料夾路徑推算編號（Chrome 的未封裝規則）。依賴 Chrome 的內部規則，不採用。

## R2 本機程式怎麼啟動（決定 D2：使用者確認 A，2026-10-14）

- **建議 A：安裝時產生 `.bat`，直接呼叫專案 `.venv` 的 python**：`@"<…\.venv\Scripts\python.exe>" -m steamsage.host --config "<…\steamsage.toml>" %*`。
  設定檔路徑在安裝時寫死（spec FR-015：要讀寫的檔案不由請求決定）。R0 H 驗證可行。不用 `uv run`：它可能先同步套件、輸出文字或連網，
  而本機程式的標準輸出只能有通道訊息。
- B：`.bat` 呼叫 `uv run --frozen --quiet steamsage host …`。每次多 uv 的啟動時間，而且 uv 的輸出不受我們控制。
- C：打包成 exe（PyInstaller 之類）。要新增建置相依套件，不採用（憲章：新增套件須有明確用途）。

細節：

- `.bat` 以系統的 OEM 字碼頁寫入（`cmd.exe` 這樣讀批次檔），所以路徑可以有中文與空白（憲章「技術約束」）；路徑無法用該字碼頁表示時，安裝指令失敗並說明。
- 本機程式啟動後**第一件事**是把真正的標準輸出留給通道、把 `sys.stdout` 與檔案描述元 1 改指向日誌，避免任何 `print` 弄壞通道。
- 本機程式檢查 Chrome 傳入的來源參數是不是登記的擴充功能（Chrome 已經檢查 `allowed_origins`，這是第二道）。

## R3 設定檔的修改方式（決定 D3：使用者確認 A，2026-10-14）

spec FR-008：只改 `[purchase_options]` 中那一款遊戲的那一行，其他內容逐位元組不變。

- **建議 A：自己寫逐行編輯，再用 `tomllib` 驗證**。009 的這個區段只有 `<App 編號> = "sub/N" | "bundle/N"`，格式固定。
  - 找到 `[purchase_options]` 區段（到下一個 `[` 開頭的表頭或檔尾為止）；在區段中找那一款遊戲的那一行（鍵可以有或沒有引號）；新增、改寫或刪除。
  - 寫入前用 `tomllib` 解析新內容並檢查：除了這款遊戲之外，整份設定解析後和原本相同；這款遊戲的值是要的值（或已經沒有）。不相同就不寫，回覆失敗。
  - 保留原本的換行（LF 或 CRLF）與檔尾換行。有 UTF-8 BOM 的檔案 `tomllib`（以及 `load_config`）本來就讀不了，視為設定檔無法解析（實作時查證，2026-10-14）。
  - 拒絕（不修改）：設定檔無法解析（FR-017）；同一款遊戲在區段中出現多次或寫在區段外（例如 `purchase_options.1091500 = …` 的寫法）；那一行跨多行。
    回覆會說明要先手動修正。
  - 新增的行放在區段最後一筆指定之後（區段尾端的註解留在最後）；區段中沒有任何指定時放在最後一個非空白行之後；區段不存在時加在檔尾（前面空一行）。
- B：新增 `tomlkit` 套件（保留格式的 TOML 讀寫）。比較通用，但多一個相依套件，而且它重新輸出整份檔案，「其他內容逐位元組不變」還是要另外驗證。

寫入的行（決定 D7：使用者確認 A，2026-10-14）：

- **建議 A**：`1091500 = "bundle/32470"   # 《電馭叛客 2077：終極版》（2026-10-14 從 Steam 頁面指定）`，和設定檔中現有那一行的寫法一致。
  名稱來自資料庫（不是請求）；寫進註解前移除控制字元與換行，長度上限 80 字。
- B：只寫 `1091500 = "bundle/32470"`，和報告「指定」欄的設定行完全相同。

兩種寫法解析後相同，所以 spec FR-012（和手動寫同一行的結果相同）都成立。

## R4 寫入鎖（決定 D4：使用者確認 A，2026-10-14；spec FR-019 已修正）

spec FR-019 寫「使用和每日更新、`report` 相同的寫入鎖」。查證後：**`report` 不取寫入鎖**（003 research R9：唯讀讀資料庫，可以和 `update` 同時執行）；
寫入鎖 `data/.lock` 只有 `update`、`reference`、`import-legacy`、`calendar` 會取。背景更新是 `update`（取鎖）→ `report`（不取鎖）→ 備份三個獨立的程序。

- **建議 A**：本機程式先取自己的處理鎖 `data/.host.lock`（另一個指定還在處理 → 「上一個指定還在處理」，FR-018），再取寫入鎖 `data/.lock`
  （被占用 → 「背景更新進行中，請稍後再試」，FR-019），兩個鎖都持有到回覆為止。兩個都用現有的 `WriterLock`（記錄 PID，擁有者已經結束的鎖可以接手）。
  沒有排除的情況：本機程式和另一個正式 `report`（手動執行，或背景更新在 `update` 結束後的那 6 秒）同時執行；這和現在「手動 `report` 與背景更新的
  `report`」可以同時執行是同一種情況。spec FR-019 已改成「和每日更新相同的寫入鎖（`report` 本身不取鎖，003 R9）」。
- B：正式 `report` 也改成取寫入鎖（被占用時等待）。可以完全排除同時執行，但改變 003 R9 的行為：手動 `report` 在 `update` 執行中要等兩分鐘，
  背景更新與 `更新資料.cmd` 的結束代碼也要重新定義。

## R5 失敗時還原哪些東西（決定 D5：使用者確認 A，2026-10-14）

`report` 依序寫：正式紀錄 → HTML 報告 → 擴充功能資料檔。只還原設定檔的話，若失敗發生在 HTML 報告寫好之後，報告與資料檔會是新版本的內容，
但設定檔已經改回來，違反 spec FR-009 的「既有的報告與資料檔維持上一次成功的版本」。

- **建議 A：還原三樣東西，正式紀錄保留**。修改設定檔之前，在記憶體中保存設定檔、`data/reports/latest.html`、擴充功能資料檔的原始內容；失敗時這三樣寫回原始內容（暫存檔再改名）。
  `report` 已經保存的正式紀錄**不刪除**（憲章 IV：每次正式執行 MUST 保存當次預測紀錄）。2026-10-14 `/speckit-analyze` C1 修正了原本「刪除這次新增的紀錄」的做法。
  影響：下一次正式報告以這份紀錄為比較基準，這款遊戲會出現一次版本更換的變動標示。相對基準，版本確實換過；這和手動 `report` 部分失敗時的行為相同。
- B：只還原設定檔；報告與資料檔維持 `report` 自己的部分成功行為。spec FR-009 要改寫。

「失敗」的定義（兩種做法相同）：`report` 結束代碼 1；或摘要中正式紀錄沒有保存（`record` 以「未保存」開頭）；或擴充功能資料檔沒有寫入
（`extension` 以「未寫入」開頭，或擴充功能資料夾不存在）。個別遊戲的決策錯誤（結束代碼 2 的其他原因）**不是**失敗：那是憲章 III 的逐項隔離，
和手動執行 `report` 相同；面板照樣顯示那款遊戲的狀態。

Chrome 在處理途中關閉（R0 沒有測到）：設定檔與每個輸出檔都是暫存檔再改名，不會出現寫到一半的檔案。最壞的情況是本機程式在「設定檔已改、報告還沒重新產生」時被結束：
這時設定檔是使用者確認過的新內容，下一次報告（手動或 02:30）就會套用，不是「半改」。查詢狀態的回覆帶這款遊戲在設定檔中的指定，
面板發現它和資料檔不一致時，顯示「設定檔已指定《…》，報告還沒重新產生」。不另做中斷紀錄與自動復原（憲章 VI）。

## R6 呼叫方式與時限（決定 D6，依原型直接採用）

- 每個請求用 `chrome.runtime.sendNativeMessage`（每次啟動一個本機程式程序、一問一答、結束）。R0 L：Worker 停止或等待超過 30 秒都不會中斷；
  不需要 `connectNative` 的長連線。
- 內容腳本不能直接呼叫本機程式（R0 C），一律經過 Service Worker。Worker 只轉送三種指令，並先檢查：送出的分頁是 `https://store.steampowered.com/app/<同一款遊戲>/`、
  遊戲在資料檔中、版本在資料檔這款遊戲的版本清單中且可指定（第一道檢查；本機程式仍以資料庫為準，FR-016）。
- 面板的 60 秒時限（FR-010）在內容腳本計時；Worker 繼續等待本機程式的回覆，收到後重新讀資料檔、更新圖示。之後打開或重新整理的頁面就是新內容。
- 成功時 Worker 回覆前先重新讀資料檔，內容腳本用新資料重畫面板與購買框的按鈕（FR-011）。

## R7 按兩下確認與真正的使用者操作（spec FR-006、FR-006a）

- 按鈕的狀態由 `lib.js` 的純函式決定（`idle` → 第一次按 → `confirm`，5 秒或按了別處 → `idle`；`confirm` 時再按 → `sending`），時間由呼叫端傳入，`node --test` 可以測。
- 內容腳本的點擊處理一律先檢查 `event.isTrusted`，不是就忽略（不改變狀態）。R0 T：6 種頁面程式的觸發方式都被擋下。
- 面板維持 011 的開放式 shadow root（端對端測試靠它檢查內容）。頁面程式看得到、也能改面板的節點，但不能產生被信任的點擊，而且最後要改哪一款遊戲、
  哪個版本，是 Worker 與本機程式各自重新檢查的。

## R8 擴充功能資料檔（spec FR-024、FR-025）

- 格式識別維持 `steamsage.extension/1`；每款遊戲新增 `versions`（只新增欄位）。舊版擴充功能的 `checkData` 只檢查既有欄位，不受影響。
- 內容由 `report/extension.py` 從決策字典的 `version.option`、`current` 與 `editions` 組成，不重算（憲章 VII）；詳見 [data-model.md](data-model.md)。
- 名稱與原因只用 `textContent` 顯示（FR-025，沿用 011）。

## R9 測試

- **pytest（測試先行）**：
  - 通道訊息：4 位元組長度＋UTF-8 JSON，長度上限，欄位與型別檢查（spec FR-014、FR-015）。
  - 設定檔逐行編輯：含註解、空行、CRLF、BOM、引號鍵、行尾註解、沒有區段、重複鍵、跨區段寫法的設定檔；每一種都比對逐位元組結果（SC-003）。
  - 本機程式的處理流程：人工資料庫與暫存設定檔；至少 20 種錯誤或惡意請求（SC-002）；兩個鎖被占用（SC-007）；在每一步注入失敗後設定檔、報告、資料檔都還原、正式紀錄保留（SC-004）；
    從本機程式指定的結果和「手動寫同一行再執行 `report`」相同（除了產生時間，SC-005）；日誌沒有金鑰（用測試金鑰值搜尋日誌）。
  - 安裝與移除：登錄操作經過可替換的介面，測試不碰真的登錄；產生的 `.bat` 與登記檔內容。
  - 擴充功能資料檔的 `versions`。
- **node --test**：版本一節的模型、按鈕狀態（含 5 秒逾時）、Worker 的轉送檢查。
- **端對端**（`tests/extension/e2e.py` 擴充）：把擴充功能複製到暫存資料夾，把本機程式名稱換成測試名稱，登記一個**假的本機程式**（固定回覆，回覆帶 `fake: true`；
  不是假的就中止），在 `Software\Chromium\…` 登記、跑完刪除。檢查：版本一節、按兩下、模擬點擊不送出、進度、成功後重畫、逾時說明、沒有安裝時的說明、購買框的捷徑、
  沒有展開就不啟動本機程式、擴充功能發出的網路請求仍為 0（SC-006、SC-008）。端對端**從不呼叫真的本機程式**，也不碰使用者的設定檔。
- **使用者的 Chrome**（quickstart）：真的安裝本機程式，在 Cyberpunk 2077 的頁面改追蹤本體、再改回終極版，比對設定檔與報告。

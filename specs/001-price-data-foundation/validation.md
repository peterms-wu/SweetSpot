# Validation: 價格資料基礎（feature 001）

**日期**：2026-09-25 | **環境**：Windows 11、Python 3.14.6、uv 0.11.26 | **分支**：`001-price-data-foundation`

- 自動測試：`uv run pytest` 共 **275 項全部通過**，涵蓋單元、契約、整合測試，全部不連網。
- 實機驗收：依 [quickstart.md](quickstart.md) 的情境，對真實的願望清單（68 款）、ITAD 與 Steam 實際執行。
- 以下「通過」只表示資料蒐集功能符合規格，**不代表任何預測準確度**（憲章「功能測試通過不等於預測準確」）。

## 區域折扣一致性（提供給 feature 002）

以全部同時有兩區資料的遊戲計算（`ALL`）：

- 逐日比較兩區折扣百分比相同的比例：**99.0%**
- 台灣區 19,930 次促銷開始中，美國區在前後 1 天內有相同折扣的比例：**95.7%**

這是「用美國區較長的折扣歷史補足台灣區」的依據（憲章 IX 要求先驗證）。是否採用、以及如何採用，由 feature 002 以回測決定。

## 實機驗收中發現並修正的問題

| 問題 | 修正 |
|---|---|
| ITAD 在 email 未驗證時，約 100 次請求就限流 | 被要求等待時暫停送出請求，最多等待一個 5 分鐘視窗；使用者後來已驗證 email |
| 「追蹤起點」只標記原價的第一筆 | 改成每個序列的第一筆都標記；schema v2 migration 更正既有資料 |
| 漏收特賣偵測以遊戲數計算，誤報 53 天 | 改以發行商數計算 |
| 漏收特賣門檻納入沒有資料的年份，誤報 30 天（本次驗收發現） | 只用資料涵蓋期間內的季節特賣計算門檻（回歸測試：`test_threshold_ignores_sales_before_the_data_starts`） |
| Steam 搜尋的總數包含套裝列、空結果回傳 start -1、翻頁位置沒有對齊 50 會被改掉 | 改用結果列數翻頁；空頁代表翻完；位置不一致時從頭重翻一次 |
| GetItems 預取每款遊戲都送出一次請求 | 改成一次查整批 50 款 |
| 套件核對每次只能查一個 Steam 商店套件 | 改用 Web API GetItems 批次查詢，核對規則不變 |
| 廣泛樣本第一次完整執行花了 7.6 小時仍未完成：稀少分層沒有停止條件，而且已滿的分層仍要逐款查詳細資料 | 預篩時就跳過年份和價位兩層都已滿的遊戲；掃完母體後接受實際數量。完整執行降為 35 分鐘 |

## 已知限制與未驗證項目

- **首次從空資料庫開始的完整更新**，沒有在所有最佳化完成後重新計時。SC-001 的數字來自開發過程中分段的實測。
- **台灣區歷史只從 2024-12-11 開始**，這是 ITAD 開始追蹤的時間。長期預測需要依賴美國區資料與參考資料集，是否可行由 feature 002 驗證。
- **Steam 商店每 5 分鐘約 200 次**的限制是社群觀察值，Valve 沒有公開，程式以 1.5 秒間隔保守執行。
- **Web API 的真實速率限制也不明**。只做過 20 次請求的小測試，程式維持 1 秒間隔。
- **2 款未發行遊戲沒有歷史，1 款 ITAD 查無歷史**，覆蓋摘要中分別標示為 `not-fetched` 和 `none`。
- **Dying Light 等 2 款在 ITAD 沒有台灣區現價**，交叉核對標示為 `missing`。

# Feature Specification: 內部識別碼改名 steamsage → sweetspot

**Feature Branch**: `016-rename-internal-ids`

**Created**: 2026-10-15

**Status**: Draft

**Input**: User description: "016 內部識別碼改名：steamsage → sweetspot（在 014 公開到 GitHub 之前）……"（全文見對話；要點整理在下方「背景」）

## 背景

- 2026-09-28 專案改名 SweetSpot，只改了顯示名稱（第 1 層）；程式指令、套件、設定檔、資料庫、日誌、擴充功能內部名稱、排程工作仍叫 `steamsage`／`SteamSage2`（第 2 層，延到秋特後）。
- 2026-10-15 使用者決定在 014（公開到 GitHub）**之前**單獨做這個 feature：公開後再改，每個使用者都要自己搬檔案；repo 叫 SweetSpot、指令卻叫 `steamsage` 會讓新使用者困惑。
- 合併後要讓每日 02:30 背景更新實際跑幾天沒有問題，才開始 014。
- 2026-10-15 的盤點（程式掃描，`specs/` 以外的版控檔案）：`steamsage` 出現在 4 個擴充功能檔、76 個 `src` 檔、137 個測試檔、3 個 scripts、5 個根目錄檔、2 份 docs 等，共 45 種不同寫法。其中有幾類是**寫進已保存資料的識別碼**，改了會讓舊資料讀不懂或讓回測資料集改變，這個 feature 刻意不改（FR-006）。

## Clarifications

### Session 2026-10-15

- Q: 只有舊名稱的設定檔或資料庫時，新程式要自動搬家，還是拒絕執行並提示？ → A: 拒絕執行並提示「請先執行搬家」，不改任何檔案；背景更新在日誌寫明原因、以有別於 0／2 的結束代碼結束。理由：搬家只在使用者看著的時候發生，排程工作、本機程式、Chrome 這些要動手的步驟不會被略過；忘記搬家的代價只是一晚的更新失敗，資料不受影響。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 程式與指令都叫 sweetspot（Priority: P1）

使用者（以及之後 014 的新使用者）用 `sweetspot` 這個名稱操作工具：`uv run sweetspot update`、`report`、`review`、`host install` 等所有指令；設定檔叫 `sweetspot.toml`、資料庫叫 `sweetspot.db`、日誌、擴充功能的資料檔與頁面上的節點都用新名稱。行為、數字與結論和改名前完全相同。

**Why this priority**: 這是 feature 的目的；沒有它就沒有可以搬的新名稱。

**Independent Test**: 在測試環境與真實資料的副本上，用新名稱執行每個指令；全部測試通過；同一份資料下，改名前後的報告、正式紀錄、擴充功能資料檔除了產生時間與檔名以外內容相同。

**Acceptance Scenarios**:

1. **Given** 一個已改名的環境，**When** 執行 `uv run sweetspot --help` 與每個子指令的說明，**Then** 說明文字中的指令與檔名都是新名稱。
2. **Given** 同一份資料庫副本，**When** 分別用改名前與改名後的程式產生正式報告，**Then** 兩份正式紀錄的決策、格式名稱與規則版本相同，HTML 報告與擴充功能資料檔除了產生時間與路徑以外相同。
3. **Given** 已保存的舊正式紀錄（格式名稱 `steamsage.decision/2` 等），**When** 新程式讀取它作為比較基準或事後對照，**Then** 照常讀取、比較，不報錯。
4. **Given** 擴充功能已重新載入，**When** 打開遊戲頁、願望清單頁與彈出視窗，**Then** 顯示與改名前相同（面板、那一行、版本一節、捷徑都在）。

---

### User Story 2 - 一次把現有環境搬到新名稱（Priority: P1）

使用者在主資料夾合併新程式之後，執行一次搬家：設定檔、資料庫、擴充功能資料檔改成新名稱，排程工作與本機程式跟著換，之後每天 02:30 照常更新。搬家前先備份，任何一步失敗都能回到搬家前的狀態。

**Why this priority**: 使用者的日常更新不能因為改名而中斷或遺失資料；沒有平順的搬家，US1 就不能合併到正在使用的主資料夾。

**Independent Test**: 在真實資料（設定檔、資料庫、紀錄、擴充功能資料檔）的副本上執行搬家，之後 `update` 與 `report` 正常；資料庫與設定檔內容逐位元組相同（只是名稱不同）；在任一步驟模擬失敗，副本回到搬家前的樣子。

**Acceptance Scenarios**:

1. **Given** 主資料夾有 `steamsage.toml`、`data/steamsage.db`、`extension/data/steamsage-extension.json`，沒有新名稱的檔案，**When** 執行搬家，**Then** 新名稱的檔案出現且內容與舊檔逐位元組相同，舊名稱的檔案不再被使用，搬家前的備份留在一個說明清楚的位置。
2. **Given** 搬家完成，**When** 下一次 02:30 背景更新執行，**Then** 它用新名稱的指令與檔案完成更新與報告，日誌寫在新名稱的日誌檔，結束代碼和平常一樣。
3. **Given** 背景更新正在寫資料庫，**When** 使用者執行搬家，**Then** 搬家立即拒絕並說明原因，任何檔案都沒有被改動。
4. **Given** 搬家在檔案改名或驗證的某一步失敗（例如資料庫檔被其他程式鎖住），**When** 搬家結束，**Then** 已經改名的檔案恢復成舊名稱，使用者看到失敗原因與目前的狀態。（排程工作、本機程式等環境步驟失敗時不改回檔案，依 FR-009a 列為手動步驟。）
5. **Given** 搬家完成，**When** 使用者照搬家結束時列出的步驟操作（重新安裝本機程式、在 Chrome 重新載入擴充功能），**Then** 015 的指定版本功能照常運作。
6. **Given** 已經搬過家，**When** 再執行一次搬家，**Then** 它說明已經是新名稱、什麼都不改。

### User Story 3 - 只有舊名稱的檔案時不會默默開新檔（Priority: P2）

舊名稱的設定檔或資料庫還在、新名稱的不在時（例如還沒搬家就跑了新程式，或從舊的雲端備份還原），任何指令都不會默默建立一個空的新設定檔或新資料庫，讓使用者以為資料不見了。

**Why this priority**: 新程式找不到新名稱的檔案時，原本的行為是建立預設設定檔與新資料庫；改名後這會變成「資料庫突然是空的」，是最可能發生、也最嚇人的錯誤。

**Independent Test**: 在只有舊名稱檔案的測試環境執行每個會讀寫設定檔或資料庫的指令，每一個都拒絕執行並提示先執行搬家（FR-010），沒有任何新檔案出現、舊檔內容不變。

**Acceptance Scenarios**:

1. **Given** 只有 `steamsage.toml` 與 `data/steamsage.db`，**When** 執行任何指令（包括 02:30 背景更新），**Then** 指令拒絕執行並提示先執行搬家（FR-010），背景更新的日誌寫明原因且結束代碼不是 0 或 2；不會出現空的 `sweetspot.toml` 或空的 `data/sweetspot.db`，舊檔內容不變。
2. **Given** 舊名稱與新名稱的檔案同時存在，**When** 執行任何指令，**Then** 使用新名稱的檔案，並提醒使用者舊檔還在（不自動刪除、不合併）。
3. **Given** 從改名前的雲端備份 zip 還原（zip 內是 `data/steamsage.db` 與 `steamsage.toml`），**When** 照還原說明操作，**Then** 能回到可以使用的狀態。

---

### User Story 4 - 確認沒有漏改（Priority: P3）

用一個程式掃描所有版控檔案，列出還有 `steamsage` 的地方；除了明確列在例外清單上的項目，結果是零。例外清單本身也由掃描產生並寫在文件中，之後 014 清理公開內容時可以直接引用。

**Why this priority**: 改名範圍大、寫法多（45 種），只靠人工找一定會漏；但漏改不會造成資料損失，所以排在搬家之後。

**Independent Test**: 執行掃描，例外清單以外的出現次數為 0；故意在一個檔案加一個 `steamsage`，掃描會找到它。

**Acceptance Scenarios**:

1. **Given** 改名完成，**When** 執行掃描，**Then** 例外清單以外的出現次數為 0，並列出每個例外的類別與理由。
2. **Given** 一個新加的、不在例外清單的 `steamsage`，**When** 執行掃描（例如在測試中），**Then** 掃描失敗並指出檔案與行號。

### Edge Cases

- **還沒搬家就跑了新程式**：合併後如果使用者忘了搬家，02:30 背景更新會用新程式碰到只有舊名稱的檔案 → 拒絕執行，那一晚的更新失敗一次、資料不受影響；使用者搬家後恢復（US3、FR-010）。
- **搬家時 Chrome 開著 Steam 頁面**：擴充功能資料檔改名後，舊版擴充功能讀不到資料檔 → 面板暫時不顯示（011 的行為），重新載入擴充功能後恢復；搬家結束的說明要提到。
- **搬家時本機程式剛好被呼叫**：本機程式的指定版本會取寫入鎖，和搬家互斥（FR-008）。
- **舊的日誌檔**：`data/logs/steamsage-YYYYMMDD.log` 是歷史紀錄，保留原名，不搬也不刪。
- **舊的資料庫升級備份**：`data/steamsage.db.bak-vN` 若存在，保留原名（說明它們是舊名稱時代的備份）；之後新的升級備份用新名稱。
- **雲端備份**：搬家後的每日備份 zip 用新檔名；舊的 zip 保持原樣（US3 情境 3）。
- **Windows 排程工作**：工作名稱改了，但排程、觸發條件、以 headless 方式執行、錯過時補跑等設定要和原本相同；改不成功時不能讓每日更新消失（保留舊工作或明確提示）。
- **專案資料夾名稱**：已經是 `〈專案資料夾〉`，不在範圍內。
- **specs/ 中過去 feature 的文件**：是歷史紀錄，不改；目前還在用的操作指引（README、HANDOFF 的操作步驟）要改成新名稱。
- **`import-legacy` 與「舊專案 SteamSage」**：指的是前身專案的名稱，不是本專案的識別碼，保留（列入例外清單）。

## Requirements *(mandatory)*

### Functional Requirements

**新名稱（US1）**

- **FR-001**: 程式的指令名稱、套件名稱 MUST 改為 `sweetspot`；所有子指令、選項與輸出行為不變。
- **FR-002**: 設定檔預設名稱 MUST 改為 `sweetspot.toml`，資料庫 MUST 改為 `data/sweetspot.db`，日誌 MUST 改為 `data/logs/sweetspot-YYYYMMDD.log`，資料庫升級前的備份 MUST 改為 `data/sweetspot.db.bak-v<舊版本>`。
- **FR-003**: 擴充功能的資料檔 MUST 改為 `extension/data/sweetspot-extension.json`；擴充功能在網頁上加入的節點名稱與內部的全域名稱 MUST 改為 SweetSpot 的名稱；畫面上顯示的內容不變。
- **FR-004**: 雙擊用的 `更新資料.cmd`、背景用的 `背景更新.cmd`、`scripts/` 中仍在使用的腳本（包括雲端備份）MUST 使用新名稱；雲端備份 zip 內的檔名 MUST 改為新名稱。
- **FR-005**: README、HANDOFF 的操作步驟與指令說明 MUST 改為新名稱；README MUST 說明舊名稱（`steamsage`、`SteamSage2`）與保留不改的資料識別碼。

**不改的資料識別碼（US1）**

- **FR-006**: 下列寫進已保存資料、或決定資料集的識別碼 MUST NOT 改變，並 MUST 在文件中列為「歷史名稱」：
  - 輸出與紀錄的格式名稱 `steamsage.<名稱>/<版本>`（例如 `steamsage.forecast/1`、`steamsage.decision/2`、`steamsage.extension/1`、`steamsage.review/1`、`steamsage.rule-backtest/1`、`steamsage.ns-backtest/1`）；
  - feature 004 調參組與驗證組的分組依據 `steamsage-004-split`（改了分組就會變，回測資料集識別碼也會變）；
  - 已保存紀錄中的欄位名稱（例如 `steamsage_version`）。
- **FR-007**: 改名前後，同一份資料產生的正式紀錄、HTML 報告與擴充功能資料檔，除了產生時間與檔案路徑以外 MUST 相同；回測資料集識別碼 MUST 不變。

**搬家（US2）**

- **FR-008**: MUST 提供一個一次性的搬家操作，把設定檔、資料庫、擴充功能資料檔改成新名稱。搬家 MUST 先取得和背景更新相同的寫入鎖；鎖被占用時 MUST 立即拒絕且不改任何檔案。
- **FR-009**: 搬家前 MUST 留下可以還原的備份（或證明改名本身不改內容、可直接改回）；檔案改名與驗證的任一步驟失敗時 MUST 把已改的檔案改回舊名稱，並說明失敗原因與目前狀態（環境步驟的失敗依 FR-009a 處理，不改回檔案）。搬家後檔案內容 MUST 與舊檔逐位元組相同。
- **FR-009a**: 搬家 MUST 處理或明確引導其餘環境：Windows 排程工作改名（排程與設定不變）、本機程式重新安裝（啟動檔指向新的套件名稱）、Chrome 擴充功能重新載入、開發環境重新同步。由程式自動完成的部分 MUST 在失敗時不讓每日更新消失；需要使用者動手的部分 MUST 在搬家結束時逐項列出。
- **FR-009b**: 已經是新名稱時，搬家 MUST 說明現況且不改任何檔案。

**舊名稱的保護（US3）**

- **FR-010**: 只有舊名稱的設定檔或資料庫、沒有新名稱的時，任何指令 MUST NOT 建立空的新設定檔或新資料庫，也 MUST NOT 自動搬家；MUST 拒絕執行，說明「找到舊名稱的檔案，請先執行搬家」並給出搬家指令，不改任何檔案。背景更新遇到時 MUST 在日誌寫明這個原因，並以非 0、和平常結果（0、2）不同的結束代碼結束。搬家本身與只顯示說明的指令（例如 `--help`）不受此限。
- **FR-011**: 新舊名稱的檔案同時存在時，MUST 使用新名稱的檔案，並提醒舊檔還在；MUST NOT 自動刪除或合併。
- **FR-012**: README MUST 說明如何從改名前的雲端備份還原。

**掃描（US4）**

- **FR-013**: MUST 有一個可重複執行的掃描，列出版控檔案中所有 `steamsage`（不分大小寫）；例外清單以外的出現次數 MUST 為 0，並作為自動測試的一部分。
- **FR-014**: 例外清單 MUST 依類別列出（資料識別碼、前身專案名稱、specs 的歷史文件、舊名稱說明等），每一類附理由；清單的內容 MUST 由掃描產生，不手寫。

**安全**

- **FR-015**: 搬家與掃描的輸出、日誌 MUST NOT 出現 API 金鑰（憲章 IX）。

### Key Entities

- **名稱對照**：舊名稱 → 新名稱的對照表（指令、套件、設定檔、資料庫、日誌、擴充功能資料檔、頁面節點、排程工作），是改名與搬家的單一依據。
- **保留的資料識別碼**：FR-006 列出的格式名稱、分組依據、紀錄欄位名稱；不隨改名改變。
- **搬家紀錄**：一次搬家做了什麼、備份在哪裡、哪些步驟要使用者自己做；失敗時記錄停在哪一步。
- **例外清單**：掃描允許留下 `steamsage` 的地方，依類別與理由分組。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 改名後全部自動測試通過，測試數量不少於改名前（不因改名刪測試）。
- **SC-002**: 在真實資料的副本上，改名前後同一份資料產生的正式紀錄的決策逐款相同（願望清單全部款數中差異 0 款；2026-10-15 為 69 款），回測資料集識別碼相同。
- **SC-003**: 在真實資料的副本上，搬家在 1 分鐘內完成；設定檔、資料庫、擴充功能資料檔與搬家前逐位元組相同；模擬失敗後副本回到搬家前的樣子（原有檔案的清單與雜湊相同；搬家建立的備份資料夾與當天日誌除外）。
- **SC-004**: 只有舊名稱檔案的情況下，所有會讀寫設定檔或資料庫的指令中，建立出空的新設定檔或新資料庫的次數為 0。
- **SC-005**: 掃描在例外清單以外找到的 `steamsage` 為 0；故意加入的一處能被找到。
- **SC-006**: 合併並搬家後，02:30 背景更新連續 3 天成功（結束代碼 0 或照常的 2），由使用者確認。
- **SC-007**: 搬家、掃描與背景更新的輸出和日誌中，API 金鑰出現 0 次。

## Assumptions

- 使用者只有一台電腦、一個主資料夾 `〈專案資料夾〉`；不需要支援多台電腦或多份設定同時搬家。
- 不保留舊指令名稱 `steamsage` 當別名：只有使用者本人在用，排程與 `.cmd` 會一起改；014 公開後的新使用者只會看到新名稱。
- `specs/` 中過去 feature 的文件（包括 quickstart、原型腳本）是歷史紀錄，不改名；015 之前留下的原型腳本若需要重跑，照文件中的舊名稱理解即可。
- 舊的日誌檔、舊的資料庫升級備份、舊的雲端備份 zip 保持原名，不改寫。
- Chrome 擴充功能需要使用者自己按「重新載入」，程式無法代勞（和 015 相同）。
- 擴充功能的固定編號（manifest `key`）與本機程式名稱 `com.sweetspot.edition` 不變。
- 合併時機由使用者決定；合併後先搬家，再讓背景更新跑幾天，之後才開始 014。

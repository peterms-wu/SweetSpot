# Spec drift 稽核：001–013、015、016（2026-10-22）

014 的稽核（[audit-2026-10-22.md](./audit-2026-10-22.md)）之後，使用者要求往前稽核到其他 spec。specs/ 會整份公開，所以在第一次公開之前做。處理記在 tasks.md Phase 10（014 T067–T080）。

## 範圍與方法

- 文件：001–013、015、016 各自的 spec、plan、data-model、research、quickstart、contracts（不含 checklists、validation 的數字、prototype）。
- 程式：現在的 `src/sweetspot/`、`scripts/`、`extension/`、兩支 .cmd、測試。
- 8 個唯讀 agent 平行比對：001；002–003；004–005；006–007；008–009；010–012；013／015／016；主線 commit 歷史（`cb1ed65` 以前的 61 個 commit）。
- 規則：016 規定過去 feature 文件裡的舊名稱是歷史紀錄，不算落差；後來的 spec、constitution、tasks 可以合法取代較早的條文，有紀錄就不算 DRIFT，但舊 contract 讀起來仍像現行規格、又沒有註記的，列為 RECORDED-ELSEWHERE。
- agent 的結論只當線索：改程式的每一項都親自核對（讀程式，能實跑的實跑），先寫一個在舊程式上會失敗的測試再修。文件補記也要求寫的人先核對程式。

## 結論

- **落差有兩個來源**：
  1. 各 feature 實作時多做的行為（旗標、欄位、邊界、文字）沒有寫進 contract；後來的 feature 改了舊 contract 的行為，卻沒有回頭加註記（002–004 最多）。
  2. 合併後直接在 master 上做、沒有自己 feature 資料夾的維運修補：雲端備份、`背景更新.cmd`、日誌結果行、輸出編碼、schema v7。014 的 contract 用「只列改變、其餘不變」接手，但「其餘」從來沒有基準。
- 2026-10-14 起擴充功能的合併後修補都在同一個 commit 回寫了主 contract，習慣是好的；它們的落差都在次要文件（別的 feature 的 contract、spec 與 quickstart、被弄斷的表格）。
- 沒有 commit hook 檢查回寫（014 稽核已記）。

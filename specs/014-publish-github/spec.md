**Feature Branch**: `014-publish-github`

**Status**: Draft

## 背景

- 使用者 2026-09-28 提出三個要求：**願望清單不寫死、移除個人資訊、安裝說明**。
- 已決定、不再重議（HANDOFF §3a，2026-09-28／2026-10-15）：
  - 清理後開**新的公開 repo，只有一個初始 commit**；本機完整歷史保留在私人備份 repo（完整 git 歷史＋HANDOFF.md；資料庫備份放在它的 Release 附件，已在每日排程）。
  - 作者 email 用 GitHub noreply 地址。
  - `specs/` 公開（清掉 SteamID 與本機路徑），`HANDOFF.md` 不公開。
  - 授權 MIT；ITAD 的價格資料另受 ITAD 條款限制，與程式碼授權無關。
  - 016 內部識別碼改名已在 2026-10-18 完成；`steamsage.<名稱>/<版本>` 等格式名稱是刻意保留的歷史名稱，README 已說明。
- 2026-10-18 重新核對的現況（程式掃描 git 追蹤的 650 個檔案）：
  - 預設設定寫死了使用者本人的 SteamID；沒有設定檔時，第一次執行會默默用這個預設值建立設定檔。網址只接受 `/wishlist/profiles/<17 位數字>/`。
  - 使用者的 SteamID 出現在 9 個追蹤檔：程式 1、測試 2、腳本 1、`specs/001` 2、`specs/011` 原型 3。
  - 本機專案路徑（〈專案資料夾〉與它的上層）出現在 47 個追蹤檔，大多在 `specs/`（含原型）；使用者家目錄路徑 1 個檔；GitHub 帳號名只在 HANDOFF.md；個人 email 不在任何追蹤檔。
  - 預設設定的「前身專案匯入」路徑是使用者本人的資料夾。
  - 測試資料有錄下來的真實回應，包括使用者的願望清單內容（遊戲、價格、指定版本）；HTML 報告的 golden 頁也是。
  - 新使用者沒有註冊每日排程的方法（目前只有 016 的搬家會重建既有的排程工作）。
  - 雲端備份依賴一個只有使用者本人才有的私人 repo；新使用者的背景更新會在這一步失敗。
  - 預測用的參考資料集是使用者的電腦每天累積的（2026-10-18 約 2,600 款，每晚預算 120 秒）；新使用者一開始只有自己的願望清單。

## Clarifications

### Session 2026-10-18（specify 時的問題）

- Q: 測試資料與 golden 頁裡錄下的使用者願望清單內容算不算要移除的個人資訊？ → A: **C＋NSFW**。(1) 處理「幾乎是完整願望清單」的兩個檔：`tests/fixtures/steam/wishlist_ok.json`（66 款，含排序與加入日期）與 `docs/model/comparisons.md` 的逐款表（61 款）；(2) Steam 內容描述為「成人性內容」或「頻繁裸露或性內容」的遊戲不出現在公開檔案（2026-10-18 實查共 9 款：4 款在測試或 specs 裡，其餘 5 款只在完整清單檔；名稱只記在私人的 HANDOFF，本文件公開不寫出）；(3) 錄下的發行商 Shiravune 搜尋結果（約 35 個露骨標題，不是使用者的願望清單）改錄或換成虛構標題；(4) 其餘零星出現的遊戲（主流遊戲當例子）保留。理由：去掉 SteamID 後連不回帳號，真正透露偏好的是完整清單與它的排序、日期；NSFW 標題公開後最容易引起誤會。
- Q: 第一次公開之後，公開 repo 和本機開發環境怎麼對應、以後怎麼更新？ → A: **本機 master 是唯一正本，公開 repo 是它的發佈快照**：清理直接做在 master；每次發佈取 master 當下的追蹤檔案扣掉排除清單，掃描與測試通過後在公開 repo 加一個 commit（第一次就是唯一的初始 commit），使用者確認才推送；每次發佈記下對應的 master commit（記在私人那邊）；個人資訊掃描成為 master 的自動測試，防止以後又寫進去。外人的 PR 不直接合併，由使用者搬回 master 後隨下次發佈出現。這取代原本「之後的同步不在範圍」的假設，同步納入本 feature。
- Q: LICENSE 的著作權人寫什麼？ → A: 使用者的 GitHub 帳號名（repo 網址本來就顯示它，不多露出資訊）。
- Q: 「在全新資料夾照 README 從頭安裝」的驗收要在哪裡做，才不會蓋掉使用者正在用的環境？ → A: 同一個 Windows 帳號、全新資料夾；擴充功能載入到另一個 Chrome 設定檔；排程用測試名稱註冊、確認後移除；本機程式從測試資料夾安裝、確認後從主資料夾重新安裝改回；白天做，不碰 02:30。理由：這台電腦是 Windows 11 Home（沒有 Sandbox／Hyper-V），每個使用者只有一個本機程式登錄、排程名稱整台共用。
- Q: 新使用者剛裝好、參考資料集幾乎是空的時候，工具要怎麼處理？ → A: README 說明可以手動執行一次參考資料集建立、否則每晚慢慢累積；參考資料集還小的時候，報告頁首與擴充功能顯示一則提示（目前幾款、怎麼補完）。只是呈現層的提示，不改預測規則、不降信心等級（不觸及憲章原則 IV）；「多小算小」由 plan 依原作者驗證時的資料集大小決定並寫明理由。
- Q: 新使用者第一次執行時還沒設 ITAD 金鑰，工具要停下來還是照樣跑？ → A: 只在第一次設定時擋下：沒有設定檔、正要詢問願望清單網址時先檢查 ITAD 金鑰，沒有就說明怎麼申請與設定、不建立設定檔；已經有設定檔的情況維持現在的行為（照跑，最後列出警示），使用者本人的每日排程不受影響。
- Q: 使用者輸入自訂網址形式時，設定檔要記錄什麼？ → A: 第一次設定時換算成數字形式（`/profiles/<17 位數字>/`）存進設定檔，並告訴使用者「已記成這個帳號」；之後不再使用自訂網址。理由：自訂網址可以改、舊的可能被別人接手，只記數字形式就永遠是同一個帳號，每晚也不用多一次查詢。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新使用者用自己的願望清單（Priority: P1）

新使用者第一次執行時，工具問他的 Steam 願望清單網址（或個人檔案網址），確認讀得到之後寫進他自己的設定檔；之後的更新、報告都是他自己的願望清單。工具裡不再有任何人的 SteamID 當預設值。

**Why this priority**: 這是使用者的第一個要求；沒有它，新使用者裝好後看到的是別人的願望清單，或什麼都跑不起來。

**Independent Test**: 在一個沒有設定檔的全新資料夾，用一個測試用的公開願望清單網址（兩種格式各一次）執行第一次更新，設定檔裡是這個網址、報告裡是這份清單；在背景（沒有人可以回答）的情況下執行，什麼檔案都沒建立並說明原因。

**Acceptance Scenarios**:

1. **Given** 全新資料夾、沒有設定檔，**When** 使用者雙擊更新並輸入 `https://store.steampowered.com/wishlist/profiles/<17 位數字>/`，**Then** 工具確認這份願望清單讀得到，建立設定檔（內含這個網址與其餘預設值），繼續完成更新與報告。
2. **Given** 同上，**When** 輸入自訂網址形式（`/wishlist/id/<名稱>/` 或個人檔案網址 `steamcommunity.com/id/<名稱>`、`steamcommunity.com/profiles/<17 位數字>`），**Then** 工具找到對應的帳號，告訴使用者已記成這個帳號，設定檔裡是數字形式的願望清單網址，結果和輸入數字形式相同。
3. **Given** 輸入的網址格式錯誤、帳號不存在或願望清單不公開，**When** 工具檢查，**Then** 說明是哪一種問題與怎麼修正（例如到 Steam 隱私設定把願望清單設為公開），讓使用者重新輸入，不建立設定檔。
4. **Given** 沒有設定檔，**When** 每日排程在背景執行，**Then** 不建立設定檔或資料庫，日誌寫明「還沒設定願望清單，請先手動執行一次」，以和平常結果不同的結束代碼結束。
5. **Given** 使用者本人既有的設定檔，**When** 合併後照常執行，**Then** 行為和合併前相同，不會被問網址。
6. **Given** 沒有設定檔、也還沒設 ITAD 金鑰，**When** 使用者雙擊更新，**Then** 在詢問網址之前就說明缺少 ITAD 金鑰、怎麼申請與設定（設定後要重開視窗），不建立設定檔（FR-014）。

### User Story 2 - 公開的內容沒有個人資訊（Priority: P1）

要公開的每一個檔案都經過程式掃描：SteamID、本機路徑、帳號名、email、API 金鑰、對話連結。除了列明理由的例外，結果是零。`specs/` 的歷史文件只把這些值換成說明性的代稱（例如「〈SteamID〉」、「〈專案資料夾〉」），內容的意思不變。

**Why this priority**: 使用者的第二個要求；公開之後就收不回來。

**Independent Test**: 對要公開的檔案執行掃描，例外清單以外為 0；在測試裡故意放進一個 SteamID、一個本機路徑與一個 email，掃描都會找到並指出檔案與行號。

**Acceptance Scenarios**:

1. **Given** 清理完成，**When** 執行掃描，**Then** 每一類（SteamID、本機路徑、帳號名、email、金鑰、對話連結）例外清單以外的出現次數為 0，並列出每個例外的類別與理由。
2. **Given** 一個新加的、不在例外清單的個人值，**When** 執行掃描（例如在測試中），**Then** 掃描失敗並指出檔案與行號。
3. **Given** 掃描到 API 金鑰的類別，**When** 掃描輸出結果，**Then** 只說「哪個檔案、第幾行有金鑰」，不印出金鑰本身。
4. **Given** 測試與測試資料，**When** 改用虛構的 SteamID 之後，**Then** 全部測試照常通過。
5. **Given** HANDOFF.md 與其他只屬於使用者本人的檔案（清單由 plan 盤點），**When** 產生公開內容，**Then** 這些檔案不在其中。

### User Story 3 - 照 README 從零安裝（Priority: P1）

一個只有 Windows 電腦的新使用者，照 README 從頭做：裝好前置工具、申請並設定金鑰、第一次更新、看報告、註冊每日背景更新、載入 Chrome 擴充功能、安裝本機程式。過程中不需要知道 README 沒寫的事。

**Why this priority**: 使用者的第三個要求；沒有它，公開的 repo 只有原作者能用。

**Independent Test**: 在同一個 Windows 帳號的全新資料夾（除了金鑰以外沒有任何本機狀態）照 README 逐步執行，到能看到自己的報告、擴充功能在另一個 Chrome 設定檔的 Steam 頁面顯示、每日排程（測試名稱）已註冊；過程中遇到 README 沒寫的步驟都記下來並補進 README。驗收結束時移除測試排程、從主資料夾重新安裝本機程式，使用者的環境回到驗收前的樣子（FR-012a）。

**Acceptance Scenarios**:

1. **Given** 一台裝好 Windows 的電腦，**When** 照 README 的「前置需求」安裝，**Then** README 列出每一個需要的工具、版本與用途，並說明哪些只有選用功能才需要。
2. **Given** 還沒有金鑰，**When** 照 README 申請與設定，**Then** README 說明哪一把是必要的、哪一把是選用的（少了會怎樣）、在哪裡申請、怎麼設成使用者層級的環境變數，以及不要寫進任何檔案。
3. **Given** 第一次更新完成，**When** 使用者看報告，**Then** README 事先說明第一次要多久，以及參考資料集還小的時候預測會怎樣、要多久或怎麼做才會完整；報告頁首與擴充功能顯示「參考資料集目前只有 N 款」的提示與補完方法（FR-014a）。
4. **Given** 參考資料集已經達到門檻（例如使用者手動補完，或每晚累積到了），**When** 下一次產生報告，**Then** 這則提示不再出現。
5. **Given** 使用者想要每天自動更新，**When** 照 README 的一個步驟註冊，**Then** 每日排程建立完成，時間與設定和原作者的相同；也有一個步驟可以移除。
6. **Given** 新使用者沒有私人備份 repo，**When** 每日背景更新跑到雲端備份這一步，**Then** 略過並在日誌寫一行說明，不算失敗、不影響整體結束代碼。
7. **Given** README，**When** 使用者讀前幾段，**Then** 知道這個工具只支援台灣區 Steam 商店與新台幣、只支援 Windows。

### User Story 4 - 發佈與更新公開 repo（Priority: P2）

本機 master 是唯一正本。使用者想公開（第一次或之後的更新）時，執行同一個發佈步驟：取 master 當下的追蹤檔案扣掉排除清單，掃描與測試通過後，在公開 repo 的工作資料夾產生一個 commit（作者是 noreply 地址），由使用者確認再推送。第一次發佈就是公開 repo 唯一的初始 commit；之後每次發佈多一個 commit。每次發佈都記下對應的 master commit。原本的主資料夾、私人備份 repo 與每日更新都不受影響。

**Why this priority**: 這是最後一步，前三個故事做好才有東西可以公開；而且它要使用者確認才會推送。

**Independent Test**: 執行發佈步驟，得到的資料夾只有一個 commit、作者是 noreply 地址、沒有 HANDOFF.md、掃描為 0；在那個資料夾照 README 安裝並跑完測試；在 master 做一個小修改後再發佈一次，公開資料夾多一個 commit、內容和 master 相同（排除清單除外）；主資料夾的 git 狀態與每日更新不變。

**Acceptance Scenarios**:

1. **Given** 清理完成、還沒公開過，**When** 執行發佈步驟，**Then** 公開資料夾的 git 歷史只有一個 commit，作者與提交者都是 noreply 地址，訊息不含對話連結。
2. **Given** 已經發佈過、master 之後有新的 commit，**When** 再執行發佈步驟，**Then** 公開資料夾多一個 commit，內容和 master 目前的追蹤檔案相同（排除清單除外），master 刪掉的檔案在公開版也刪掉；訊息說明這次對應的範圍，不含對話連結。
3. **Given** 要發佈的內容裡有掃描不通過的項目，**When** 執行發佈步驟，**Then** 不建立 commit，並列出問題。
4. **Given** 發佈步驟完成，**When** 還沒得到使用者的確認，**Then** 不建立公開 repo、不推送任何東西。
5. **Given** 每次發佈，**When** 完成，**Then** 私人那邊留下「這次發佈對應 master 的哪個 commit」的紀錄，下一次發佈以它為起點。
6. **Given** 發佈與公開都完成，**When** 之後每天 02:30，**Then** 使用者本人的背景更新、雲端備份照常，結束代碼和平常一樣。

### Edge Cases

- **自訂網址之後被改掉或被別人接手**：設定檔只記數字形式（FR-002），所以每日更新永遠是同一個帳號，不會默默改抓別人的清單。
- **輸入的是願望清單以外的 Steam 網址**（商店頁、群組）→ 說明格式，讓使用者重新輸入。
- **雙擊後關掉視窗沒有輸入** → 不建立設定檔，下次再問。
- **願望清單是空的** → 照常建立設定檔，報告說明清單是空的。
- **新使用者沒有設 ITAD 金鑰**：歷史價格是預測的必要資料 → 第一次設定時就擋下並說明怎麼申請、設定（FR-014），不要跑完才發現每款都沒有預測。
- **設好金鑰後忘了重開視窗**：使用者層級環境變數要在新開的視窗才讀得到 → 說明裡要提到「設定後關掉再重開」。
- **沒有 Steam Web API 金鑰**：參考資料集的廣泛樣本會停用 → README 說明影響，更新照常完成。
- **新使用者沒有安裝 gh 或沒有私人 repo** → 雲端備份略過（US3 情境 5），不出錯。
- **「前身專案匯入」**：只對有前身專案資料的人有用 → 預設值不得是任何人的本機路徑；沒有設定時這個指令說明它的用途並結束。
- **測試資料裡錄下的真實回應**：除了 SteamID 等識別值，還有使用者的願望清單內容 → 處理方式見 FR-008。
- **以後重新錄測試資料**：錄製腳本會再錄一次真實的願望清單回應；排序、加入日期與 NSFW 遊戲不是 SteamID 那種掃描抓得到的值 → 錄製時就要去掉（FR-008a）。
- **願望清單之後加了 NSFW 遊戲**：只影響使用者本機的資料庫與報告（不進 git）；只有被寫進測試資料或文件時才需要擋（FR-008b）。
- **外人在公開 repo 開 PR 或 issue**：公開 repo 不是開發的地方 → README 或貢獻說明寫明 PR 由作者搬回後隨下次發佈出現。
- **master 刪掉或改名的檔案**：發佈時公開版也跟著刪掉或改名，不留下舊檔。
- **`specs/` 裡的原型腳本有寫死的本機路徑**：換成代稱後腳本不能直接執行 → 它們是歷史紀錄，不需要能重跑；在 `specs/` 的說明裡註明。
- **擴充功能的固定編號**：manifest 的 `key` 是公鑰，公開沒有問題；如果任何私鑰檔存在，MUST NOT 公開（由掃描確認）。
- **使用者本人以後繼續開發**：照常在 master 開發；要更新公開版就再執行一次發佈步驟（US4）。新的 feature 寫進個人值時，master 的自動測試會先失敗（FR-016b）。

## Requirements *(mandatory)*

### Functional Requirements

**願望清單（US1）**

- **FR-001**: 預設設定 MUST NOT 含任何人的 SteamID 或願望清單網址。沒有設定檔時，有人可以回答的執行（雙擊更新、在終端機執行指令）MUST 詢問願望清單網址，確認讀得到之後才建立設定檔；沒有人可以回答的執行（每日排程）MUST NOT 建立設定檔或資料庫，MUST 在日誌寫明原因並以非 0、和平常結果不同的結束代碼結束。
- **FR-002**: MUST 接受願望清單網址與個人檔案網址的數字形式（`/profiles/<17 位數字>`）與自訂網址形式（`/id/<名稱>`）；自訂網址 MUST 在設定時換算成對應帳號的數字形式，設定檔 MUST 只記錄數字形式的願望清單網址，並告訴使用者已記成哪個帳號；結果和輸入數字形式相同。之後的更新 MUST NOT 再使用自訂網址。
- **FR-003**: 網址格式錯誤、帳號不存在、願望清單不公開時 MUST 分別說明原因與修正方式，MUST NOT 建立設定檔。
- **FR-004**: 已經有設定檔的使用者（包括原作者本人）MUST NOT 被問網址，行為不變。

**個人資訊（US2）**

- **FR-005**: MUST 有一個可重複執行的掃描，檢查要公開的每一個檔案，類別至少包括：SteamID、本機使用者與專案路徑、GitHub 帳號名、email 地址、API 金鑰的值、對話連結、私鑰檔。每一處 MUST 列出檔案與行號；金鑰 MUST 只報位置不印值。例外清單 MUST 依類別附理由，內容由掃描產生，不手寫。不需要真實金鑰的類別 MUST 作為自動測試的一部分。
- **FR-006**: `specs/` 與 `docs/` 中的 SteamID、本機路徑、帳號名 MUST 換成說明性的代稱；除此之外歷史文件的內容不改（這是 016「specs/ 歷史文件不改」的明確例外）。
- **FR-007**: 程式、測試、腳本與測試資料中使用者的 SteamID MUST 換成虛構的值；全部測試 MUST 照常通過。
- **FR-008**: 公開的檔案 MUST NOT 含使用者的完整願望清單或它的排序、加入日期：`tests/fixtures/steam/wishlist_ok.json` MUST 改成只含測試用得到的項目、排序與日期為虛構值；`docs/model/comparisons.md` 的逐款表 MUST 改成不列遊戲名稱（代號或只留統計），結論與數字不變。其餘零星當例子的遊戲保留。
- **FR-008a**: 測試資料的錄製腳本 MUST 在錄製時去掉願望清單的排序與加入日期、並排除 FR-008b 的遊戲；錄發行商搜尋結果時 MUST 不再錄 Shiravune（改錄另一家沒有這類作品的發行商，或錄完一律換成虛構標題），讓重新錄製不會把它們帶回來。
- **FR-008b**: Steam 內容描述為「成人性內容」或「頻繁裸露或性內容」的遊戲 MUST NOT 出現在公開的檔案中（名稱或 app id）；現有的 MUST 換成沒有這類描述的遊戲或代號，相關測試照常通過。錄下的發行商 Shiravune 搜尋結果 MUST 改錄另一家沒有這類作品的發行商，或把標題換成虛構名稱。發佈步驟 MUST 檢查這一項（判斷依 Steam 公開的內容描述，查詢方式由 plan 決定）。
- **FR-009**: HANDOFF.md 與其他只屬於使用者本人的檔案 MUST NOT 公開；清單由 plan 依盤點結果列出，並由發佈步驟（FR-016）強制排除。
- **FR-010**: 「前身專案匯入」的預設路徑 MUST NOT 是任何人的本機路徑；沒有設定時這個指令 MUST 說明用途並以非 0 結束，不影響其他指令。

**安裝與日常（US3）**

- **FR-011**: README MUST 有一段從零開始的安裝說明，涵蓋：前置工具與版本（標明哪些只有選用功能需要）、兩把金鑰（必要或選用、少了會怎樣、在哪裡申請、怎麼設成使用者層級環境變數）、第一次更新與參考資料集（要多久、資料集還小時預測的狀態、怎麼讓它完整）、每日背景更新的註冊與移除、Chrome 擴充功能的載入、本機程式的安裝、只支援台灣區與 Windows。
- **FR-012**: MUST 提供一個步驟註冊每日背景更新、一個步驟移除；建立出的排程（時間、背景執行、錯過時補跑等設定）MUST 和原作者現在的排程相同。
- **FR-012a**: 註冊步驟 MUST 能指定排程工作的名稱（預設是「SweetSpot 每日背景更新」）；同名的工作已經存在、而且指向別的資料夾時，MUST 說明並拒絕，除非使用者明確要求取代。這讓從零安裝的驗收能在使用者本人的電腦上用測試名稱進行，不蓋掉每日更新。
- **FR-013**: 沒有私人備份 repo 的環境，每日背景更新 MUST 略過雲端備份並在日誌寫一行說明；這 MUST NOT 算失敗或改變整體結束代碼。使用者本人的雲端備份 MUST 照常。
- **FR-014**: 沒有設定檔、要詢問願望清單網址時（FR-001），MUST 先檢查 ITAD 金鑰；沒有時 MUST 說明怎麼申請與設定成使用者層級環境變數、MUST NOT 建立設定檔，讓新使用者不會跑完第一次更新才發現。已經有設定檔時 MUST 維持現在的行為：照常更新，缺少的金鑰列在警示中。
- **FR-014a**: 參考資料集的款數低於門檻時，報告頁首與擴充功能 MUST 顯示一則提示：目前幾款、門檻是多少、怎麼補完（手動建立一次，或等每晚累積）。這是呈現層的提示，MUST NOT 改變預測、甜蜜價或信心等級；兩個呈現層 MUST 顯示同樣的款數（憲章 VII）。門檻 MUST 依原作者驗證模型時的資料集大小決定，理由寫在 plan；plan MUST 確認原作者本人目前的資料集是否在門檻以上（預期在以上，不會看到提示）。
  - **修訂（2026-10-22，014 T048；從零安裝驗收發現）**：抽樣已經做完（相關樣本的公司目錄都翻完並選完，廣泛樣本各分層都滿或已看過整份 Steam 遊戲清單）而款數仍低於門檻時，提示 MUST 改說「已補完」與實際款數，MUST NOT 再建議執行建立參考資料集的指令（再執行也不會增加）。驗收時新安裝做完是 1,659 款。
- **FR-015**: MUST 有 LICENSE（MIT，著作權人是使用者的 GitHub 帳號名；這是帳號名掃描的明確例外），README MUST 說明 ITAD 價格資料另受 ITAD 條款限制、與程式碼授權無關，以及每個使用者要用自己的金鑰。

**發佈與更新公開 repo（US4）**

- **FR-016**: 本機 master MUST 是唯一正本；清理（FR-006～FR-010）MUST 直接做在 master。MUST 有一個發佈步驟，第一次與之後每次都用它：把 master 當下的追蹤檔案扣掉排除清單（FR-009）放進公開 repo 的工作資料夾（master 刪掉的檔案也刪掉），執行掃描（FR-005、FR-008b）與自動測試，全部通過才建立一個 commit；作者與提交者 MUST 是 noreply 地址，訊息 MUST NOT 含對話連結。任何一項不通過 MUST NOT 建立 commit。第一次發佈的 commit 就是公開 repo 唯一的初始 commit。
- **FR-016a**: 每次發佈 MUST 在私人那邊（不公開的檔案或私人 repo）記下對應的 master commit 與發佈時間；下一次發佈 MUST 以它為起點，說明這次包含的範圍。
- **FR-016b**: 個人資訊掃描中不需要真實金鑰、網路或使用者本機資料（設定檔、資料庫）的類別 MUST 是 master 的自動測試，讓之後的 feature 寫進個人值時在本機就失敗；帳號名只讀 repo 本身的 git remote，屬於這一類。
- **FR-017**: 建立公開 repo 與推送 MUST 由使用者確認後才做；發佈步驟 MUST NOT 改動主資料夾的檔案與 git 狀態（發佈紀錄的 tag 除外，FR-016a）、私人備份 repo 或每日排程。
- **FR-018**: 公開的內容 MUST 能照 README 安裝並通過全部自動測試。
- **FR-018a**: README（或貢獻說明）MUST 寫明公開 repo 是發佈快照：外人的 PR 不直接合併，由作者搬回後隨下次發佈出現。

**安全**

- **FR-019**: API 金鑰 MUST NOT 出現在任何輸出、日誌、設定檔或公開的檔案中（憲章 IX）；第一次執行詢問網址的流程 MUST NOT 詢問或保存 Steam 密碼或登入資訊。

### Key Entities

- **要公開的檔案清單**：由 master 追蹤的檔案扣掉排除清單（FR-009）得到；發佈步驟與掃描都以它為準。
- **個人值的類別**：SteamID、本機路徑、帳號名、email、金鑰、對話連結、私鑰、NSFW 遊戲（FR-008b）；每一類有辨識方式與代稱。
- **發佈紀錄**：每次發佈對應的 master commit、公開 repo 的 commit、時間；只存在私人那邊。
- **例外清單**：掃描允許留下的地方，依類別與理由分組，由掃描產生。
- **使用者的設定檔**：只在使用者自己的資料夾、不進版本控制；第一次執行時由詢問的結果建立。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 全部自動測試通過，測試數量不少於清理前（不因清理刪測試）。
- **SC-002**: 對公開內容執行掃描，每一類在例外清單以外的出現次數為 0；故意加入的 SteamID、本機路徑、email 各一處都被找到。Steam 內容描述為「成人性內容」或「頻繁裸露或性內容」的遊戲在公開內容中出現 0 次；使用者願望清單的排序與加入日期出現 0 次。
- **SC-003**: 在全新資料夾照 README 安裝（同一個 Windows 帳號、另一個 Chrome 設定檔、測試名稱的排程），從開始到看到自己的第一份報告，不需要 README 以外的資訊；實測的時間記在 README（第一次更新與參考資料集分開記）。驗收後使用者的排程工作與本機程式登錄和驗收前相同，當晚 02:30 照常成功。
- **SC-004**: 沒有設定檔的情況下，使用到別人的願望清單 0 次；背景執行建立出的設定檔或資料庫 0 個。
- **SC-005**: 第一次公開後，公開 repo 只有 1 個 commit，作者與提交者是 noreply 地址，不含 HANDOFF.md；在 master 做一個測試用的小修改再發佈，公開 repo 多 1 個 commit，內容與 master 的追蹤檔案（排除清單除外）逐檔相同（這項在第一次推送之前、於本機的公開資料夾驗證，驗完還原，不推送測試用的 commit）。
- **SC-006**: 合併後，使用者本人的 02:30 背景更新連續 3 天成功（結束代碼 0 或照常的 2），雲端備份照常上傳，由使用者確認。
- **SC-007**: 所有輸出、日誌與公開檔案中，API 金鑰出現 0 次。

## Assumptions

- 公開 repo 在使用者自己的 GitHub 帳號下、名稱 SweetSpot；repo 的網址本身會顯示帳號名，這不算要移除的個人資訊（要移除的是檔案內容裡的帳號名）。
- 公開的文件與介面維持繁體中文（只支援台灣區，使用者是台灣的 Steam 玩家）；README 開頭可以有一兩句英文說明。
- spec-kit 的工具檔（`.specify/`、`.claude/skills/`）一起公開：`specs/` 是用它產生的，留著讓讀者看得懂流程；plan 盤點時若發現個人內容，照 FR-006 處理。
- 新使用者只有一台 Windows 電腦，裝了 Chrome；不需要支援 macOS、Linux 或其他瀏覽器。
- 參考資料集不隨 repo 散布（含 ITAD 的價格資料，受 ITAD 條款限制）；每個使用者在自己的電腦上建立。
- 原作者在公開後仍在主資料夾與私人備份 repo 工作；公開 repo 只透過發佈步驟更新（US4）。
- 清理只改測試資料、文件與預設設定；使用者本機的資料庫、預測紀錄、回測與報告不受影響，之後加入願望清單的遊戲照常進資料庫與回測。
- 合併時機由使用者決定；這個 feature 不改預測規則、模型或資料格式。

## 範圍外

- 發佈到 Chrome 線上應用程式商店、PyPI 套件。
- 支援台灣以外的區域（憲章 IX）、macOS／Linux。
- 在公開 repo 上直接開發，或自動把公開 repo 的 PR 合併回 master。

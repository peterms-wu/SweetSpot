# Research: 甜蜜價決策與 HTML 報告（feature 003）

**日期**：2026-09-25 | **資料**：`data/steamsage.db`（2,871 款商品、68 款願望清單）、現行模型 `seasonal-freq` 1.0.0

每一節的格式：決定、理由、考慮過的替代方案。R0 是 plan 階段在真實資料上的探索，其餘各節的依據多半來自這裡。

## R0 探索：真實資料上的決策規則試算與簡易回測

用約 150 行的原型腳本（不進版控）在真實資料上跑決策規則。規則照 spec，並已套用 plan 探索後的 3 個決定。

|---|---|---|---|---|
| 16 | 27 | 11 | 11 | 3 |

- 預測加決策共 3.2–4.7 秒，其中預測約 3 秒。
- 所有現價都在 24 小時內取得。

現在買改為和甜蜜價比、原價不一致改列低信心、低信心組標出回測到價率。

## R1 決策規則的計算方式

**決定**：規則 `sweet-price` v1.0.0，全部以整數運算：

1. **曲線範圍**：一般信心取全部時點；低信心只取結束時間 ≤ 分析時點 + 12 個月（`add_months`）的時點，和回測的評估窗口相同。
2. **P_min**：範圍內最後一個時點，累積機率 ≥ 0.5 的最深等級；沒有任何等級達到時為 0。
3. **P_min 為 0 的一般信心遊戲**改走低信心路徑：用 R2 的「無本身歷史曲線」，範圍 12 個月，重算 P_min。
4. **容許差距**，以分為單位：`tol = min(max(ceil(原價 × g / 100), 3000), 10000)`。
   - g 在 P_min < 分界（75）時為 10，否則為 5。
   - 分界、g、下限、上限都來自使用者偏好（R11）。
5. **目標價** = `原價 × (100 − P_min) / 100 + tol`。
   **目標折扣** = 滿足 `原價 × (100 − d) ≤ 目標價 × 100` 的最小 d（LEVELS 中）。兩邊都乘開，不用浮點數。
6. **甜蜜價** = 目標折扣的價格，也就是 `原價 × (100 − 目標折扣) / 100`，以分為單位並無條件捨去到分。
7. **甜蜜時點** = 範圍內，目標折扣的累積機率第一次 ≥ 0.5 的時點。依定義一定存在，因為目標折扣比 P_min 淺；
   不存在時記為決策錯誤（不影響其他遊戲）。
8. **等待對照表**：時點 1 到甜蜜時點，每個時點「累積機率 ≥ 0.5 的最深等級」、其價格與機率。「現在買」也列出時點 1。
9. **分組**，依序判斷：
   1. 無法預測
   2. 現在買：現價已知，而且 ≤ 甜蜜價
   3. 低信心：信心為低、P_min=0 改走低信心、或原價不一致（R3）
   4. 即將到價：甜蜜時點落在前 `soon_sales` 場，預設 1
   5. 繼續等
10. **台幣顯示值**：決策核心以「元」四捨五入（0.5 進位）算好放進契約；呈現層不計算（憲章 VII）。

**理由**：

- 整數運算讓「剛好等於」的邊界（例如原價 369、-10% 加 10pp）不受浮點誤差影響，也和手算一致（SC-001）。
- 目標折扣取 LEVELS 中的等級，和曲線的語意一致：「≥ -d% 的機率」。

**替代方案**：以浮點數計算再四捨五入。邊界會不穩定，不採用。

## R2 P_min 為 0 時的整體比例曲線從哪裡來

**決定**：預測引擎在每一批預測加一條「沒有本身歷史時的預測」。做法是用現行模型對一個沒有任何歷史的證據呼叫 `predict()`，
以選用欄位 `no_history` 放在 `steamsage.forecast/1` 的最上層：

```json
"no_history": {"confidence": "low", "reasons": ["…"], "probabilities": [[…]]}
```

時點與整批相同。

**理由**：

- 決策核心不需要知道模型內部，所以換成 feature 004 的模型也適用。
- 對 `seasonal-freq` 來說，這就是整體比例曲線。
- 新增選用欄位不改契約版本（forecast-output 契約的規則），002 的 contract test 不受影響。

**替代方案**：

- 從任一款低信心遊戲借曲線：沒有低信心遊戲時就沒有。不採用。
- 在決策核心重算整體比例：等於重做模型的工作，違反憲章 VII。不採用。

## R3 現價、原價與取得時間

**決定**：

- **現價**：分析時點以前、該遊戲台灣區**任一來源**（`steam-current` 或 ITAD）最新的一筆觀測，使用 `PriceStore.observations()`，會排除隔離的資料。
  現價 = `price_cents`；原價 = 同一筆的 `regular_cents`。沒有 `regular_cents` 時，用預測的 `regular_price_cents`。
- **確認時間**：取以下兩者中較晚的，且不超過分析時點：
  - 最新一筆 `steam-current` 的 `observed_at`
  - ITAD 歷史的 `history_known_until`
- **過舊**：分析時點 − 確認時間 > 24 小時，就標示「現價可能已變」。24 小時是規則常數，寫在模型定義文件。
- **原價不一致**（FR-037）：現價的原價 ≠ 預測的 `regular_price_cents`（ITAD 序列在分析時點的原價），且兩者都已知。
  這時以現價的原價換算，加標籤，決策改為低信心。

**理由**：

- `steam-current` 是本工具每次更新時直接向 Steam 取得的價格，最接近「現在買得到的價格」。
- ITAD 歷史可能停在舊的套件（例如 Dying Light）。
- 用「確認時間」而不是觀測時間：ITAD 的 `observed_at` 是價格改變的時間，不是確認的時間。

**替代方案**：只用 ITAD 序列的狀態當現價。Dying Light 會變成原價 NT$300、-70%，和 Steam 實際的 NT$670、-80% 不同。不採用。

**已知限制**：以過去時點執行時，ITAD 資料列的 `retrieved_at` 可能晚於分析時點。這種執行只供檢查，不是正式紀錄，
規則回測（R10）也不使用現價，而是用 ITAD 序列在分析時點的狀態。

## R4 季節特賣以外的折扣紀錄（FR-007）

**決定**：

- 範圍：分析時點以前的 ITAD 台灣序列。
- 找出和任何已結束季節特賣都沒有重疊的折扣狀態，取最深的一個。
- 只有**比本身季節特賣紀錄的最深折扣更深**時才寫進原因，格式為「季節特賣以外出現過 -X%（YYYY-MM-DD），模型不預測這類折扣」。沒有季節特賣紀錄時視為 0。

**理由**：

- 目的是揭露「模型沒看到、但比它看到的更深」的折扣。每款都列會變成雜訊。
- 實測願望清單有 16 款符合，包含 PRAGMATA 與 Skyrim SE。

**替代方案**：一律列出。大多數遊戲的發行商促銷不比季節特賣深，列了反而掩蓋重點。不採用，spec FR-007 已依此修正。

## R5 決策契約 `steamsage.decision/1`

**決定**：

- 一次執行產生一份 JSON，內容包含：
  - 完整的預測 `steamsage.forecast/1`
  - 規則名稱、版本與規則常數
  - 使用者偏好的值
  - 每款遊戲的決策
  - 比較基準與變動
  - 資料更新狀態
  - 規則回測的引用數字
  - 各組款數
- 格式見 [contracts/decision-output.md](contracts/decision-output.md)。
- 預測紀錄就是這份 JSON 的 gzip 壓縮檔。報告只讀這份 JSON。

**理由**：

- 一份檔案同時是「報告的輸入」與「正式紀錄」，所以報告和紀錄一定一致（SC-003）。
- 日後對照實際價格時，需要的東西（曲線、現價、原價、決策）都在同一處。

**替代方案**：紀錄只存預測，決策另外存。兩份檔案可能不同步，不採用。

## R6 預測紀錄與比較基準

**決定**：

- **路徑**：`data/forecasts/<分析時點 UTC，%Y%m%dT%H%M%SZ>.json.gz`。
- **寫入**：先寫 `<名稱>.tmp`，完成後用 `os.replace` 改名。gzip 的 `mtime=0`，所以同樣的內容會得到同樣的位元組。
- **列出**：只列 `*.json.gz`，所以不完整的 `.tmp` 永遠不會被當成紀錄。
- **比較基準**（FR-019）：分析時點換算成台北時間後的日期，早於本次日期的紀錄中，分析時點最晚的一份。
  打不開、JSON 無效或 schema 不符的紀錄一律略過，並在報告中註明略過了哪些檔案。
- **正式紀錄**：分析時點為「現在」的執行（沒有 `--as-of`）。有 `--as-of` 時不寫紀錄，也不找比較基準。

**理由**：

- 檔名依時間排序，不需要索引檔。
- 改名是原子操作，中斷時只會留下 `.tmp`（憲章 III）。

**替代方案**：資料庫新表。使用者已選擇檔案。檔案也不需要資料庫遷移，而且不碰價格資料庫（002 FR-035 的精神）。

## R7 變動標示

**決定**：以 `app_id` 比對，標示 3 種變動，並附上次的值：

- **分組**不同
- **甜蜜時點**不同：比較時點名稱，例如「2027 春特」。現在買的時點視為「現在」。
- **甜蜜價**的台幣顯示值（元）不同。

版本或偏好的差異寫在頁首的比較說明中。比較基準中沒有這款遊戲時，不標示任何變動（FR-020）。

**理由**：

- 用顯示值（元）比較，避免分的差異造成使用者看不出來的「變動」。

## R8 HTML 報告

**決定**：

- **產生方式**：只用標準庫。所有外部文字一律經過 `html.escape`（憲章 IX）。CSS 與少量 JavaScript 內嵌在同一個檔案，不引用任何外部資源（FR-027）。
- **版面**：
  - 頁首：版本、時間、偏好、提示、比較基準。
  - 每組一個 `<details open>`，標題顯示款數與規則回測的到價率。
  - 每款遊戲一個 `<details>`，摘要列放主要欄位，展開後是原因與等待對照表。
  - 名稱篩選框用 JavaScript 隱藏不符合的列。
  - 支援系統的深色模式。
- **排序**：
  - 現在買：現價由低到高。
  - 即將到價：依甜蜜價。
  - 繼續等：依甜蜜時點，再依名稱。
  - 低信心：依名稱。
  - 無法預測：依狀態。
- **路徑**：正式執行寫到 `data/reports/latest.html`，每次覆蓋。`--as-of` 寫到 `data/reports/asof-YYYY-MM-DD.html`。也可以用 `--out` 指定。
- **模組邊界**：報告模組只接受決策契約的 dict，不匯入 `forecast` 或 `decision`（contract test 檢查匯入）。

**理由**：

- 內容是表格加上可展開的細節，不需要樣板引擎。不新增相依套件（憲章：新增套件須有明確用途）。
- 估計 68 款約 100–200 KB，500 款約 1–1.5 MB，瀏覽器可以直接開。實測寫進 validation。

**替代方案**：Jinja2。多一個相依套件，但好處不大，不採用。

## R9 CLI 與一鍵執行

**決定**：

- **`steamsage report [--as-of 日期] [--out 檔案] [--open] [--update-exit N]`**：
  - 依序執行：預測 → 決策 → 找比較基準 → 寫紀錄（正式執行）→ 寫報告。
  - 以唯讀方式讀資料庫、不取寫入鎖，可以和 `update` 同時執行。
  - `--update-exit` 是 `更新資料.cmd` 傳入的 update 結束代碼（0/1/2/3），會寫進契約的 `data_refresh`，報告頁首依此說明。
  - `--open` 在完成後用系統預設程式開啟報告（`os.startfile`）。
- **結束代碼**：
  - 0：完成。
  - 2：完成但有需要注意的項目，例如 `model-error`、決策錯誤、紀錄寫入失敗、略過損壞的紀錄、update 不是 0。
  - 1：失敗，例如資料庫無法開啟、報告無法寫入。
- **`steamsage backtest-rule [--cutoff 日期] [--apps-limit N]`**：規則回測（R10），結果寫到 `data/backtests/`。
- **`更新資料.cmd`**：
  1. 執行 `uv run steamsage update`，記下結束代碼。
  2. 執行 `uv run steamsage report --open --update-exit %code%`。update 失敗（1）或已在執行（3）也照樣執行，由 report 判斷資料庫能不能讀。
  3. 依兩個結束代碼顯示中文訊息。

**理由**：

- report 保持唯讀，所以「另一個更新正在執行」時也能出報告（US4 情境 3）。
- 把 update 的結果傳進去，報告才能說明「本次資料更新未完成」（FR-031）。

**替代方案**：新增一個 `steamsage run`，在同一個程序裡跑 update 加 report。要重寫鎖的處理，而且 update 的錯誤處理已經很完整，不採用。

## R10 甜蜜價規則回測（US5）

**決定**：

- 沿用 002 的台灣區回測資料集，包括遊戲、排程、截止時間與資料集識別碼，也沿用 `load_games` 與 `predict_one`。
- 每個分析時點的做法：
  - 用現行模型預測。
  - 以 ITAD 序列在分析時點的狀態當現價與原價，做決策（不看 `steam-current`，避免洩漏）。
- 評分：
  - **到價**：甜蜜時點落在 12 個月的窗口內時，看目標折扣的第一次跨越，是否早於該特賣實際結束。已發生、未發生、截斷的判定沿用 002 的 `unit_outcome`。
  - **時間誤差**：預測的甜蜜時點減去實際跨越所在的特賣，單位是場。
  - **現在買的後續**：分析時點之後有完整 12 個月資料時，看 12 個月內有沒有出現比現在更深的折扣，以及多省的台幣金額（中位數、75 百分位、90 百分位）。
  - **超出窗口**的甜蜜時點只計數，不評分。
- 分組：依信心與分組（即將到價、繼續等、低信心），各自報告到價率與樣本數。
- 結果格式 `steamsage.rule-backtest/1`，見 [contracts/rule-backtest-result.md](contracts/rule-backtest-result.md)。
- 決策契約中的規則回測數字，放在程式常數 `RULE_BACKTEST`，並要和模型定義文件一致（有測試檢查）。
- 美國區不做：規則以台幣容許差距決定目標，美國區沒有台幣。

**理由**：原型已驗證可行，耗時約 11 秒。沿用資料集才能和 002 的分數對照。

## R11 使用者偏好設定

**決定**：在 `steamsage.toml` 新增 `[preferences]` 區段。預設值寫在 `DEFAULT_TOML`；舊設定檔沒有這一段時，自動套用預設值：

```toml
[preferences]
gap_pp_shallow = 10       # P_min 比分界淺時的折扣差距（百分點）
gap_pp_deep = 5           # P_min 達到分界或更深時的折扣差距
gap_boundary_pct = 75     # 分界：P_min ≥ -75% 算「深」
tolerance_min_twd = 30    # 容許差距下限（元）
tolerance_max_twd = 100   # 容許差距上限（元）
soon_sales = 1            # 甜蜜時點在前幾場算「即將到價」
```

驗證規則：

- 全部是正整數。
- `gap_pp_*` 介於 1–50。
- 分界介於 5–95，而且是 5 的倍數。
- 下限 ≤ 上限。
- `soon_sales` 介於 1–4。

**理由**：

- 設定檔已有「預設值合併」機制，所以不需要改使用者的舊檔。
- 規則門檻（50%、50%、12 個月、24 小時）不放在設定檔（FR-036）。

## R12 效能估算

| 步驟 | 實測或估計 |
|---|---|

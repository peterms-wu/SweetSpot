## R1 購買選項與版本的判定

- **Decision**：每日更新在 006 的版本步驟之後，接著執行「購買選項步驟」：
  1. 重用版本步驟取得的所有購買選項（套件與組合包、現價與原價），不另外請求。
  2. 內容：套件用 006 的 `version_packages`；組合包新增 `bundle_contents`（GetItems `bundleid`）。
  3. 內容中其他 App 的類型（DLC 與它的本體）用 `app_kinds`；類型是靜態事實，沿用 30 天內購買選項紀錄中的值（R8）。
  4. **版本** = 內容包含這個 App，而且其他每個 App 都是「類型 DLC、本體是這個 App」。預設購買選項照 006 處理，不重複判定。
  5. 版本才查 ITAD 商品（`sub/N`、`bundle/N`）、別名與驗證（R2），以及 ITAD 的 Steam 現價筆數。
- **Rationale**：重用 006 的來源與驗證，只新增組合包內容一個介面。含其他遊戲與不含本體的選項不查 ITAD（spec FR-001）。
- **Alternatives**：用 App 的 DLC 清單判定（要多一種請求，且清單可能不完整）；用名稱判定（不可靠，被拒絕）。
- **注意**：組合包內其他 App 的類型 MUST NOT 透過 `products`／`product_facts` 保存。那兩張表的 App 會進入參考資料的範圍
  （`reference_apps`），會改變整體比例與回測資料集。類型只存在購買選項紀錄的 `contents_json`。

## R2 驗證的擴充（組合包）

- **Decision**：`verify_version` 新增參數「被驗證的購買選項」（`sub/N` 或 `bundle/N`）：
  - ITAD 商品的別名中，**等於這個購買選項本身**的 `bundle/N` 可以接受（它的內容已在 R1 確認只有本體與自己的 DLC）；其他 `bundle/…` 仍拒絕。
  - 價格比對的基準改成「這個購買選項自己的台灣區價格」；006 的預設選項驗證行為不變（基準就是預設選項）。
  - 其他規則（`app/…` 別名、套件內容、無法公開查詢只警告）不變。
- **Rationale**：P1 上 12/12 個 BO 通過、Dying Light 十週年完整版仍被拒絕（別名是另一個組合包）。
- **Alternatives**：組合包一律拒絕（006 的做法；9 款的版本無法指定）；接受任何組合包別名（會混入含其他遊戲的組合包價格）。
- 驗證結果沿用 006 的快取：同一個 ITAD 商品 7 天內（`mapping_days`）的驗證沿用，保留原始驗證時間。

## R3 儲存

- **Decision**：
  1. **新表 `purchase_options`**（只新增）：每次每日更新、每款遊戲、每個購買選項一列（data-model §1）。
  2. **版本的價格歷史**寫進 `price_observations`：`app_id` = 願望清單的 App，`external_id` = 版本的 ITAD 商品，
     **來源 `itad-option-history`**；抓取紀錄寫 `history_fetches`，來源 `itad-option`。
  3. 資料庫升為 **schema v4**：只新增表與觸發器，沒有補值；沿用 006 的自動備份（`steamsage.db.bak-v3`）。
  4. **讀取修正**（P3 發現的必要修正）：
     - `latest_observations`、`observations`：`itad-option-history` 和 ITAD 歷史來源一樣依商品過濾，不得被當成商店現價。
     - `history_is_fresh`（不帶商品時）、`fetch_state`、`coverage`：只計來源 `itad` 的抓取紀錄。
     - 其他讀取（季節特賣偵測 `calendar.py`、`consistency.py`、`reference.py`、回測資料集）都只讀 ITAD 歷史來源，自動忽略版本歷史；
       測試逐一確認。
- **Rationale**：
  - 用獨立的來源名稱，既有的每個讀取都不受影響：P3 的 B0／B 與真實資料庫逐款相同，資料集識別碼不變。
  - 仍然依 `(app_id, external_id)` 保存，讀取版本歷史時可以直接重用 `load_games`、「已知至」與停止追蹤的判定。
- **Alternatives**：
  - 用同一個來源 `itad-history`：季節特賣偵測等不依商品過濾的讀取會混入版本的歷史，被拒絕。
  - 另開一張觀測表：安全，但讀取路徑要複製一份，被拒絕。
- **只新增**：`purchase_options` 加入 `APPEND_ONLY_TABLES`。

## R4 指定的解析與讀取

- **設定**：`steamsage.toml` 新增 `[purchase_options]`，鍵是 App 編號（字串），值是 `"sub/<數字>"` 或 `"bundle/<數字>"`。
  讀取設定時檢查格式；格式錯、鍵不是數字、同一 App 重複時忽略該行並產生警告（FR-008）。範本附註解與範例（全部註解掉）。
- **解析**（每次產生預測時，依 as_of）：對每個有指定的 App，取 `checked_at ≤ as_of` 最新一次購買選項步驟的紀錄：

  | 情況 | 結果（來源、原因代碼） |
  |---|---|
  | 指定的選項在紀錄中、是版本、通過驗證 | 追蹤它（`user`） |
  | 不在購買選項中 | 退回預設（`user-fallback`, `not-offered`） |
  | 不是版本（含其他遊戲、不含本體） | 退回預設（`user-fallback`, `not-edition`） |
  | ITAD 沒有對應商品 | 退回預設（`user-fallback`, `not-in-itad`） |
  | 驗證未通過 | 退回預設（`user-fallback`, `rejected`，附拒絕理由） |
  | 這個時點沒有購買選項紀錄（本 feature 之前、步驟被略過） | 退回預設（`user-fallback`, `no-record`） |
  | App 不在追蹤範圍 | 忽略並警告（FR-008） |

  指定的選項剛好是 Steam 預設時，來源仍是 `user`，之後 Steam 換預設也不跟著換（FR-006）。
- **以過去時點執行（`--as-of`）**：用**目前的設定**，搭配當時已記錄的購買選項。設定是使用者偏好，和 `[preferences]` 一樣不按時間記錄；
  過去時點的報告只供檢查（003）。正式紀錄中保存當時追蹤的選項與來源（R6），追溯以紀錄為準。
  這修改了 spec 的一條 Edge Case（原寫「使用當時記錄的追蹤版本與來源」）；使用者 2026-09-27 同意（plan 的決定 D1）。
- **讀取**：
  - 全部遊戲照舊用預設版本讀取一次（整體比例、非季節預測的整體比例、回測都不變）。
  - 指定生效的遊戲另外用版本的 ITAD 商品與 `itad-option-history` 來源讀一次；如果版本的商品就是目前預設版本的商品，直接用預設的資料。
  - `run_forecast`、`ns_forecast` 新增「只用來產生這款遊戲證據」的參數；整體比例只從預設版本計算。P3：其他 58 款逐款相同。
  - 目前的 Dying Light 情況（版本步驟換版本）不受影響：預設版本仍由 006 的 `history_keys` 決定。
- **Alternatives**：把指定也寫進 `app_versions`（混淆「Steam 的事實」與「使用者偏好」，被拒絕）；
  在每日更新時決定並記錄（設定改了要等下一次更新才生效，和 spec US1「下一次產生報告時」不符，被拒絕）。

## R5 現價

- **Decision**：指定生效的遊戲，現價取「最新一次購買選項紀錄中這個選項的價格」與「版本歷史的最新一筆」中較新者；
  確認時間是那一列的時間，過期判定（`STALE_HOURS`）不變。原價不一致的判定改成和版本歷史的原價比較。
- **Rationale**：購買選項紀錄就是 Steam 台灣區商店當天的價格（和 006 的預設選項價格同一個請求），不需要另外請求。
- **Alternatives**：把選項價格也寫成 `steam-current` 觀測（會和預設版本的現價混在一起，被拒絕）。

## R6 輸出與變動

- **Decision**（契約不升版，只新增選用欄位；contracts/outputs-options.md）：
  - 預測與決策的 `version` 新增：`source`（`steam-default`、`user`、`user-fallback`）、`option`（`{kind, id, name}`）、
    `fallback`（`{code, detail, requested}`）。
  - 決策新增 `editions`：這款遊戲除了追蹤的版本以外的版本（含驗證未通過的同遊戲版本），每個附名稱、編號、現價、原價、
    台灣區歷史最低價與日期、歷史起點、驗證結果、指定用的設定行（`config_line`，只有可指定的版本才有）。
    設定行由核心產生，報告只顯示（憲章 VII）。
  - 變動（`changes.py`）：和前一次正式紀錄比較「追蹤的購買選項」（kind＋id），不同時 `change.version` 新增 `cause`：
    `user`（使用者指定）、`unset`（取消指定）、`fallback`（指定不能用）、`steam`（Steam 換預設，006 的情況）。
    前一次紀錄沒有 `option`（本 feature 之前）時，用它的 `package_id` 視為 `sub/<id>`。
- **Rationale**：沿用 006 的欄位與「只在第一份報告標示」的做法；舊紀錄照樣可讀。

## R7 報告

- 摘要行：有其他版本時顯示「另有 N 個版本」（clarify）。
- 展開內容：
  - 版本清單的每一列：名稱、現價、原價、台灣區歷史最低價（日期）、歷史起點；可指定的附設定行與複製按鈕，未通過的附原因。
  - 已指定時，清單第一列是 Steam 預設版本，並說明「刪掉設定檔中的這一行即可取消指定」。
- 名稱下方的版本行：來源是 `user` 時一律顯示「追蹤 X（使用者指定）」；退回預設時顯示原因。
- 變動標示：「版本更換（使用者指定／取消指定／指定的版本不能用／Steam 換了預設）：舊 → 新」。

## R8 效能與抓取策略

| 項目 | 做法 | 預估 |
|---|---|---|
| 購買選項 | 重用版本步驟的請求 | 0 秒 |
| 組合包內容 | 每天查（偵測內容改變） | 約 3 秒 |
| 組合包內 App 的類型 | 30 天內的紀錄沿用，只查新出現的 App | 平常約 0 秒；第一次約 7 秒 |
| ITAD 對應、別名、現價筆數 | 每天 | 約 1.5 秒 |
| 別名套件的驗證 | 同一商品 7 天內沿用 | 平常約 0 秒；第一次約 3 秒 |
| 版本的台灣區歷史 | 每天（`history_hours` = 24） | 約 14 秒（32 個） |
| 版本的美國區歷史 | **只抓指定生效的版本**（決定 D2） | 每個約 0.4 秒 |

- **平常一天多約 19 秒，第一次約 29 秒**（SC-008 上限 30 秒）。報告的目標：增加 < 0.5 秒。實際耗時寫入驗收文件。
- **D2**：美國區歷史只抓指定生效的版本。所有版本都抓的話每天再多約 13.5 秒，會超過 SC-008。
  代價：剛改設定、還沒執行每日更新就產生報告時，指定版本沒有美國區的輔助證據，原因寫出「美國區歷史下一次更新才會取得」。

## R9 測試（測試先行）

- 判定與驗證：人工 GetItems 回應（`tests/fixtures/steam/`），涵蓋套件版本、只含本體與 DLC 的組合包、含其他遊戲、不含本體、
  別名是另一個組合包（Dying Light 十週年）、價格不同的別名。
- 儲存：v3 → v4 遷移前後逐表比對；`purchase_options` 只新增。
- 讀取修正：構造「版本歷史比 Steam 現價新」的資料，預設版本的現價不變（證明抓得到 P3 的潛在錯誤）；
  季節特賣偵測、區域一致性、回測資料集在加入版本歷史前後相同。
- 解析：R4 表格的每一種情況；過去時點不會看到之後的購買選項紀錄（洩漏測試證明抓得到偷看）。
- 整體比例：指定一款遊戲後，其他遊戲的預測與決策逐款相同（人工資料＋真實資料的驗收）。
- 契約與報告：人工契約 dict 產生報告並比對；變動的四種 `cause`。
